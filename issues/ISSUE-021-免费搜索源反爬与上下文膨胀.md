# ISSUE-021 免费搜索源反爬 + LLM 反复抓取导致上下文膨胀

- **日期**：2026-08-13
- **状态**：✅已解决（降级 + 限流缓解，稳定方案需搜索 API）
- **影响**：中（联网搜索能力可用，但复杂问题会反复尝试）

## 现象

1. 百度频繁抓取后返回「百度安全验证」页（HTML 1438 字节，无结果），web_search 全返回 0 条
2. LLM 问「RTX 5090 详细规格参数」时，反复 web_search ×N + web_fetch ×N，卡到 max_steps 或上下文膨胀后 LLM 输出异常 fallback

## 根因

1. **免费搜索引擎反爬**：百度对频繁请求触发安全验证（ISSUE-002/020 的延续）；DuckDuckGo 被墙；Bing 302 重定向
2. **现代网站 JS 渲染**：web_fetch 抓 nvidia.cn 等现代站，返回的是导航 + 脚本渲染前的空壳，正文清洗后质量差（"Menu"开头 7 万字导航），LLM 找不到规格表就反复换 URL 抓
3. **LLM 反复尝试 → 上下文膨胀**：每步工具结果（尤其 web_fetch 正文 3000 字）都进 messages，10 步后上下文爆炸，LLM 输出异常触发 fallback

## 解决方案

1. **Bing 作主源**（cn.bing.com，国内可达、真实 URL + 摘要），百度作降级；进程内 60 秒缓存减少重复请求
2. **web_fetch 抓取失败/质量差时 prompt 限制**：SYSTEM_PROMPT 明确「最多试 2 次，优先基于搜索摘要回答」
3. **步数上限诚实兜底**：qa/其他场景已调工具未收敛时，返回「已尽力搜索，可换问题或给链接」而非「步数上限」文案
4. sanitize 对 web_fetch 放宽到 3000 字符（不按默认 200 截断）

## 局限（挂账）

- 免费源质量有限：Bing 摘要无「规格表」式结构化数据，复杂问题提炼效果一般
- **稳定方案是搜索 API**（Tavily/Serper/Brave，带 AI 摘要），需 key —— 用户提供的参考方案①已预留 `_search_api` 扩展点

## 设计原则

- 免费搜索引擎只能作「线索」，不能保证「事实」；价格仍以本地库 live 价为锚
- 工具反复调用是上下文爆炸的根源，prompt 层要明确「快速收敛、勿反复试」
