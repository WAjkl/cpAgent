> **这一版和之前有什么不同：**

# 怎么用这份文档

## 三个时间档

| 你有多少时间 | 看哪几部分 |
|---|---|
| **进门前 3 分钟** | 只有第一部分（四样东西 + 三句不能说） |
| **提前一小时** | 第二、三部分（自我介绍 + 项目），出声念两遍 |
| **提前一天** | 四、五、六部分（问答 + AI 用法 + 岗位针对性） |

## 两个标记怎么读

**① 括号里的解释是给你看的，不要念出来**

比如你会看到：

> 「我用了 **SSE**（服务器边算边往浏览器推的技术，像对方一直跟你汇报，你不用反复问）来做流式输出。」

念的时候只说「我用了 SSE 来做流式输出」，括号里那句是帮你理解的。

**② 追问分两级**

- **追问 A** —— 大概率会问，必须准备
- **追问 B** —— 只有他刨根问底时才会问，准备了就是加分项

# 第一部分：进门前 3 分钟

## 1.1 只记这四样

**① 一句话定调（开场就用）**

> 「我是岭南师范学院软件工程 2027 届，方向是 **AI 应用开发**（不是研究算法，是把现成的模型做成能用的系统），偏全栈。这半年做了三个能跑起来的项目，两个开源，能全职实习到明年 6 月。」

**② 一个能立住的差异化（被问优势时用）**

> 「我不是训练模型的人，我是把模型做成能用的系统的人。」

> 📌 这句话为什么有力：绝大多数应届生会说「我熟悉大模型」，但说不清自己在大模型这条链上站在哪个位置。你一句话把自己定位在「工程侧」，既不吹也不虚。

**③ 三个必问的问题（轮到你时用）**

> ① 「7 天试岗有薪资吗？按什么标准算？」
> ② 「公司主营是定制开发，还是 AI 教培那块也占比较大？」
> ③ 「团队现在几个开发？我进来负责什么模块？」

**④ AI 用法一句话（被问"你怎么用 AI 写代码"时用）**

> 「我用 AI 做执行，不用 AI 做判断。样板代码交给它，架构和取舍我自己定。」

## 1.2 三句不能说

| 别说 | 为什么 |
|---|---|
| 「我没实习经历，所以……」 | 别自己先扣分。直接讲你做过什么 |
| 「这个我不太清楚，我回去学」 | 太空。改成「这块我没做过，我理解是 X，让我做会先 Y」 |
| 「我在自学 AI」 | 听起来像没产出。改成「我做了三个项目，两个开源」 |

# 第二部分：自我介绍

## 2.0 先搞懂三个词（不然念出来也是空的）

**全栈**（frontend + backend 都能写）：前端是用户看到的界面，后端是服务器上的逻辑和数据库。行业里多数人只做一边，两边都能做叫全栈。

**Agent**（智能体）：能自己判断"下一步做什么"的 AI 程序。普通程序的路是写死的（第一步查库、第二步算价），Agent 是运行时自己决定下一步该干嘛。代价是不确定性，所以要给它加限制。

**ReAct**（Reason + Act 的合成词，读「瑞-艾克特」）：Agent 的一种工作方式——**想一下 → 做个动作（调工具）→ 看结果 → 再想**，循环到能回答为止。你的 cpAgent 就是手写的这个循环。

## 2.1 三十秒版（电话、HR 初筛、被说"简单说一下"时用）

> 「岭南师范学院软件工程 2027 届，方向是 AI 应用开发。
>
> 这半年做了三个能跑起来的项目，两个开源、都带**单测**（给每块代码写自动检查，改完跑一遍就知道有没有把原来的功能弄坏）和 **CI**（每次提交代码机器自动跑一遍检查，不合格不让合进主分支）。
>
> 最贴贵司这个岗位的是一个桌面装机顾问 **Agent**，**前端**（用户看到的界面）用 **Electron**（把网页技术打包成桌面软件的壳，VS Code 就是这么做的）+ **React**（写界面的工具库）+ **TypeScript**（给 JavaScript 加了类型检查的版本，写错字段名当场报错），**后端**（服务器上的逻辑）用 **FastAPI**（Python 写接口的框架），从界面到接口到数据库都是我一个人写的。
>
> 我在佛山，通勤大概 40 分钟，每周 5 天，能一直做到明年 6 月。」

**为什么这么说**：四句话四件事——我是谁、我做过什么、哪个最贴你、我什么时候能来。不多说一句。

## 2.2 九十秒版（正式面试开场，最常用）

> 「岭南师范学院软件工程 2027 届，方向是 AI 应用开发，偏全栈。
>
> 这半年我独立做了三个能跑起来的 AI 项目，两个开源、都有单测和 CI：一个是安全告警的自动研判，一个是桌面装机顾问 Agent，还有一个用 **Dify**（一个可视化搭 AI 工作流的平台）+ **n8n**（读「n-八-n」，一个自动化流程编排工具）把校内制度做成了可评测的知识库问答。
>
> 最贴贵司这个岗位的是装机顾问那个。它有一个我觉得比较关键的设计：**配置单不是模型拼的，是确定性算法拼的——模型只出参数，不碰价格**。
>
> 为什么要这么做：模型会"编"——它不知道某张显卡现在多少钱，但会给你编一个看起来很像的数字。而价格错了，整张单子就废了。所以我把价格从模型的输出里彻底拿掉了，它想编也没有地方编。同一需求连跑 5 次结果完全一致，8000 预算实配 7875。
>
> 我的位置在算法和产品之间：不是训练模型，是把模型封装成稳定接口，让它的产出可预期、成本可算。
>
> 我在佛山，通勤 40 分钟，每周 5 天，能做到明年 6 月。」

## 2.3 三分钟版（技术面，被说"详细讲讲"）

在 90 秒版基础上，中间插两段：

> **插一段技术难点**：
> 「这个项目技术上最难的一处是防止模型编造价格。我最后不是靠**提示词**（给模型的指令，包括角色设定、格式要求这些）解决的，是**改架构**——配置单由确定性算法拼装，价格从数据库取。这样从结构上就不可能编。
>
> 这里有个认知转变：提示词是"求模型别犯错"，架构是"让它没有机会犯错"。前者是概率，后者是保证。」

> **插一段取舍**：
> 「另一个是检索方案的选择。我做过四组对照：纯词法、纯**向量**（把文字变成一串数字，意思相近的数字也相近，于是能算"像不像"）、**RRF**（读 R-R-F，一种把两路检索结果按名次融合的方法）、加同义词。
>
> 结论是**在我这个规模上不该上向量检索**——一次**embedding**（把文字转向量的那个计算过程）要几百毫秒，会顶穿我的延迟预算；而我的文档库只有几十条，词法匹配的召回已经够了。
>
> 架构上我留了口子：规模上去了就切。所以准确说法是『现在不该上』，不是『向量不好』。」

## 2.4 三档的区别（别用错）

| 场合 | 用哪档 | 核心目的 |
|---|---|---|
| 电话/HR 初筛 | 30 秒 | 让对方知道"这人可以聊" |
| 正式面试开场 | 90 秒 | 立住专业形象 |
| 技术面"详细讲讲" | 3 分钟 | 展示技术深度和取舍能力 |

> ⚠️ **用错会掉分**：90 秒的话在电话里讲完，HR 会不耐烦；30 秒的话在技术面讲，会显得没货。

## 2.5 自我介绍的两层追问

**追问 A：「你说你独立做了三个项目，具体独立到什么程度？」**

> 「从需求定义到代码到文档都是我。前端界面、组件拆分、状态管理，后端接口、数据库表、部署脚本，还有 README 和单元测试，没有第二个人。
>
> 所以每个技术决定为什么这么做我都能说出当时的取舍，包括做得不好的地方——比如我前端手写了很多样式，后来发现该用组件库。」

**追问 B：「一个人做，你怎么知道自己做对了？」**

> 「两道外力。一是单元测试，27 个，覆盖窗口裁剪、阈值判断这些核心逻辑；二是评测集，比如校规问答那个我建了 25 条测试题，里面有 4 类是陷阱题。
>
> 测试和评测集不会替我判断，但能把我漏掉的情况暴露出来。自己审自己最大的问题不是不认真，是想不到。」

# 第三部分：项目介绍

## 3.0 先记这个通用骨架（讲任何项目都用它）

**八步**：背景（为什么做）→ 一句话定位（是什么）→ 整体链路（怎么跑）→ 我做的那部分 → 一个技术难点 → 一个取舍 → 结果（数字）→ 复盘（重做会改什么）

> ⚠️ **最容易犯的错**：上来就报技术栈。"用了 FastAPI、React、Redis、Docker……"——面试官记不住，也不关心。
> **正确顺序**：先说解决什么问题，再说怎么做。

## 3.1 cpAgent（装机顾问 Agent）—— 主推项目

### 3.1.1 三十秒版

> 「用户输入一句『8000 打游戏 2K 不要显示器』，它输出一张完整配置单。
>
> 前端 Electron + React + TypeScript，后端 FastAPI + 手写的 **ReAct 循环**（想一步→调一个工具→看结果→再想，最多 12 步）。整条链路都是我一个人写的。」

### 3.1.2 两分钟版

> 「背景是我自己装机的时候，发现网上那些配置单要么过期、要么是广告。所以做了一个能按预算和用途自动出单的工具。
>
> **链路**：用户说一句话 → 提取约束（预算、用途、分辨率）→ Agent 循环决定调哪个工具（查**硬件库**（本地存了 90 条配件的型号、规格和价格，每条带来源和抓取时间）/ 抓电商价 / 联网搜）→ 拿到数据后由确定性算法拼出配置单 → 做兼容性校验 → 输出。
>
> **前端**用 Electron + React + TS，**SSE**（服务器边算边往浏览器推，不用等全部算完）接流式，用户能看到它一步步在调工具，而不是干等 10 秒。
>
> **结果**：同一需求连跑 5 次结果完全一致，8000 预算实配 7875，6 类配件全部带价格来源和抓取时间。」

### 3.1.3 五分钟版（加两个故事）

在 2 分钟版基础上加：

> **故事一（架构怎么改的）**：
> 「第一版我是让模型直接输出整张配置单的 **JSON**（一种数据格式，键值对的结构化文本）。跑几次就出问题了——同一需求跑五次给五个不同结果，有时 8000 预算配出 9200，理由是『觉得可以超一点』。
>
> 我一开始想靠提示词约束，加了『严格不要超过预算』这类话，**没用**。后来才想明白：这不是提示词的问题，是架构的问题。我把价格从模型的输出里彻底拿掉了——模型只负责决定『选哪个档次』，配置单由算法按约束拼。它想编也没有地方编。」
>
> **故事二（踩过的坑）**：
> 「还有一个坑：模型对数字不敏感。你让它填预算，这轮填 8000，下轮填 7000，理由是『觉得花掉 1000』。它不报错，但整套配置就错了。
>
> 所以我加了『**确定性注入**』——预算、用途这些关键值以**工作记忆**（程序里存当前这轮对话上下文的地方）里的为准，模型填什么都被覆盖掉。」

### 3.1.4 这个项目的三层追问

**追问 A：「模型不碰价格，那它到底负责什么？」**

> 「三件事：听懂需求（把『8000 打游戏 2K』解析成预算、用途、分辨率）、决定调哪个工具、以及最后用自然语言解释这张单子为什么这么配。
>
> 换句话说，它负责『理解』和『表达』，不负责『计算』和『选取』。」

**追问 B：「那如果硬件库里没有合适的配件，怎么办？」**

> 「两种情况。如果预算太紧，算法会给出『加 200 能上一个档次』这类提示；如果某个品类库里没有匹配项，会在 **warnings**（结果里单独列的警告列表）里说明『这个品类用的是估算价』或者『没有找到符合预算的型号』，而不是硬凑一个。
>
> 这里的取舍是：**宁可告诉用户"这个配不出来"，也不给一个看起来完整但价格是错的单子。**」

### 3.1.5 如果被追问"这算全栈吗"

> 「算。前端界面、组件拆分、状态管理，后端接口、数据库、部署脚本，还有 README 和测试，全是我一个人做的。中间没有第二个人。」

## 3.2 安全告警研判系统（Sectriage）—— 最能讲工程深度

### 3.2.0 先搞懂几个词

**告警**：安全设备发现可疑行为时发出的通知。问题是太多了，一个中型企业一天几千到几万条，人看不过来。

**降噪**：把大量重复的告警合并成少数"事件"。你以为这是模型干的？不是，是规则干的——这是面试时要主动说清的。

**指纹**：给每条告警算一个唯一标识（这里用 sha1(IP + 规则号) 取前 32 位）。同一个 IP 触发同一条规则，算出来的指纹一样，就能被识别为"同一类"。

**滑动窗口**：不是"整点算一次"，而是"从当前时刻往回数 10 分钟"。窗口随着时间往前滑，所以叫滑动窗口。

**置信度**：模型对"这个判断有多可信"打的分，0 到 1 之间。低于阈值就转人工。

### 3.2.1 三十秒版

> 「安全运营里告警太多、人看不过来。我把 3000 条告警按指纹和 10 分钟时间窗聚成 40 个事件，再用模型给每个事件出判定和依据，按风险分三档路由——置信度低于 0.8 转人工。」

### 3.2.2 两分钟版

> 「**四层链路**：聚合（指纹 + 10 分钟窗）→ 富化（补上资产信息、基线）→ 研判（检索 SOP + 规则和模型双模）→ 决策（三档路由）。
>
> **关键是把两段分清楚**：聚合是纯规则、不调模型；研判才用模型。所以降噪率 98.7% 是规则的功劳，我不拿它当模型效果讲。
>
> **工程上**：27 个单测、CI 六关（其中一关是评测门槛，核心指标跌出区间流水线直接红）、**Docker**（把程序和环境打包成箱子，搬到哪都能跑）用**非 root**（容器默认用最高权限跑，一旦被攻破等于把整台机器交出去；改成普通用户权限，同样漏洞损失有限）。
>
> 后来我还把存储层重做了一遍：窗口状态从进程内存迁到 **Redis**（把数据放内存里的数据库，因为不读磁盘所以极快，常用来做缓存和计数器），明细落 **MySQL**（传统的关系型数据库，数据存磁盘），三表六索引。」

### 3.2.3 最该主动讲的一段（加分）

> 「我做这个项目最大的收获是学会**把规则和模型分开**。一开始我想全用模型，结果发现聚合这种确定性的事，模型做又慢又不稳。
>
> 分开之后，系统变得可解释了——每个事件的降噪是规则做的，判断是模型做的，谁的责任很清楚。
>
> 这个思路后来还用在了 cpAgent 上：配置单是算法拼的，解释是模型写的。**同一个模式，用在两个项目上。**」

### 3.2.4 三层追问

**追问 A：「你说降噪是规则的功劳，那模型到底贡献了什么？」**

> 「三件事：给每个事件定性（真攻击 / 误报 / 待确认）、给出判定依据、以及高置信度时自动关闭。
>
> 降噪是规则做的，**判断是模型做的**，两者不能混。我不拿规则的效果去吹模型。」

**追问 B：「如果规则写错了，导致两个不同的攻击被聚成一个事件，怎么办？」**

> 「这会漏报，是纯指纹聚合的固有代价。
>
> 我的处理是：一，把聚合的规则做成可配置的（时间窗、阈值都能调）；二，在报告里明确写出这个局限——换 IP 打同一台机器会被拆成多簇，而换端口则会因为 IP 归一化被合到一起。
>
> 要根治得上行为相似度分析，但那样就牺牲了确定性：换个模型版本簇就变了，98.7% 这个数字也就不可比了。」

## 3.3 校规知识库问答（Dify + n8n）

### 3.3.0 先搞懂两个词

**知识库问答**：用户问问题，系统先从你的文档里找出相关段落，再让模型照着这些段落回答。这样模型不会瞎编，因为它是"照着材料答"而不是"凭记忆答"。

**溯源**：每个答案后面能指出"这句话来自哪份文件的第几条"。没有溯源，用户没法验证，也就没法信任。

### 3.3.1 三十秒版

> 「用 Dify + n8n 把校内 34 份制度做成可评测的知识库问答。四段链路：查询改写 → 依据原文作答 → 自检分流 → 多轮记忆。每个答案能溯源到文件名和条款号。」

### 3.3.2 该讲的重点（不是功能，是方法）

> 「这个项目我最想讲的不是它多好用，是**我怎么否定自己一个功能**。
>
> 我加了自检环节，感觉应该能提升质量。但我做了 **A/B 测试**（把功能开着和关着各跑一批，对比结果）——难题集跑下来，准确率没有提升，成本反而高了 2.2 倍。所以我把它默认关掉了。
>
> 这件事让我明白：**功能该不该留，不能靠感觉，要靠数据。**」

### 3.3.3 三层追问

## 4.2 项目深挖（10 问）

### Q6 你这个项目解决什么问题？

> 「安全运营里告警太多、人看不过来。一个中型企业一天几千到几万条，真正要处理的可能只有几十个。
>
> 我把 3000 条原始告警先按指纹和 10 分钟窗聚成 40 个事件，再用模型给每个事件出判定、置信度和依据，最后按风险分三档路由——置信度低于 0.8 转人工。」

**追问 A：「3000 条这个量级真实吗？」**

> 「真实环境一天几千到几万条都常见。我取 3000 是为了控制变量做对照。
>
> 量级本身不代表难度，**分布**才代表——如果 3000 条全是同一个 IP 的重复扫描，那很容易聚；如果是 3000 种不同的攻击手法，那才难。我的数据集是刻意做成混合分布的。」

**追问 B：「人工看 1.7 小时还是很久，为什么不再压？」**

> 「这 1.7 小时是『必须人看』的部分，也就是置信度低于 0.8 的那些。剩下的自动关了。
>
> 再压就只有一条路：提高自动关单的置信度阈值。但那会把该看的也放过去——安全场景里漏报的代价比误报贵得多，我宁愿人累一点。」

---

### Q7 这个降噪率 98.7% 怎么算的？

> 「3000 条聚成 40 个事件，3000 减 40 再除以 3000。
>
> **但更重要的是后半句：这一步是纯规则、不调模型，所以 98.7% 是聚类的功劳，跟 LLM 没关系。我不拿它当模型效果讲。**」

**追问 A：「那你这 98.7% 是不是没什么技术含量？」**

> 「聚合本身确实不难，难的是**知道它该由规则做而不是模型做**，以及知道这个数字不能算在模型头上。
>
> 行业里很常见的做法是把降噪率当 AI 效果宣传，我觉得那样经不起追问——面试官一问『你这步调模型了吗』就露馅了。」

**追问 B：「如果客户拿这个数字去汇报，你会怎么提醒他？」**

> 「我会明确告诉他这是"聚合压缩比"，不是"模型准确率"。真实的效果指标应该是：判定准确率、误报率、以及人工复核的工作量下降多少。
>
> 这几个数字我都能给，但它们不是同一个东西，混着讲会出问题。」

---

### Q8 为什么不用向量检索？现在不都用向量吗

> 「评估过，不选，但不是因为向量不好。
>
> **一是延迟**——一次 embedding 要几百毫秒，会顶穿我 2.5 秒的 **P95**（95% 的请求在这个时间内完成，衡量延迟的常用指标）预算。
> **二是规模**——我的 SOP 库只有几十条，词法匹配的召回已经够了。
>
> 用它等于为了解决一个我还没有的问题，先引入一个真实的成本。
>
> 而且架构上我留了口子：规模超过阈值就切向量，两路并行用 RRF 融合。准确说法是『现在不该上』，不是『向量不好』。」

**追问 A：「RRF 具体是怎么融合的？」**

> 「RRF 全称 Reciprocal Rank Fusion，倒数排名融合。
>
> 做法是不看两路的原始分数（因为词法的分数和向量的分数不是一个尺度，没法直接比），**只看名次**：某个文档在词法里排第 3、在向量里排第 7，就给它算 1/(60+3) + 1/(60+7)。60 是论文里的经验值，作用是压平名次差异。
>
> 好处是不用归一化，两路怎么打分都能融。」

**追问 B：「你怎么证明不用向量是对的？有没有可能你错过了更好的效果？」**

> 「做了四组对照：纯词法、纯向量、RRF 融合、加同义词扩展，用同一套 21 条查询评测。
>
> 结果是小库上纯词法不比向量差，融合略好但延迟翻倍。**这个结论只对我这个规模成立，我不外推。**
>
> 如果有人说『在我们的场景向量明显更好』，我完全信——因为语料口语化、同义词多的时候，向量确实更强。我这是制度文本，用词很规范。」

---

### Q9 指纹聚合具体怎么做的？

> 「三步：给每条告警算**指纹**（sha1(IP + 规则号) 取前 32 位）→ 按 10 分钟窗把同指纹的告警切成簇 → 簇内只保留首末时间和计数。
>
> 为什么用哈希不用拼字符串：定长 32 字节，索引更紧凑；作为 Redis 的 key 也更短、更快。
>
> **但它有个明确的代价**：攻击者换个 IP 打同一台机器，就会被拆成多簇。这是纯指纹聚合的固有缺陷，我认。」

**追问 A：「那为什么不用行为相似度来聚类？」**

> 「会牺牲确定性。行为相似度通常靠向量算，换个模型版本簇就变了，那 98.7% 这个数字就没法做前后对比了。
>
> 我这个系统的一个核心要求是「同一个输入永远给同一个结果」，因为安全场景要能复盘、要能解释「为什么这两条被合并了」。规则能做到，聚类做不到。」

**追问 B：「哈希碰撞了怎么办？」**

> 「sha1 取前 32 位，在百万级数据下碰撞概率极低。就算碰了，后果是两个不同的告警被合到一个簇——代价是多看几条，比漏报轻。
>
> 这是个刻意的取舍：我宁可把不同东西合到一起（人多看几眼），也不愿把同一个东西拆开（那就漏了）。」

---

### Q10 存储层为什么要重做？

> 「因为原来窗口状态在进程内存里，两个硬伤：**重启就丢、多实例各数各的**。
>
> 我做了个实验：灌 3 条同指纹告警、重启服务、再灌 2 条。内存版计数从 3 归零只剩 2，永远凑不到阈值 5，**这次攻击就漏了**。
>
> 所以我把它迁到 Redis 的 **ZSet**（有序集合，每个成员带一个分数，Redis 自动按分数排序）——member 是告警 id、score 是毫秒时间戳，每次写入先砍掉滑出窗口的，再数剩下的。」

**追问 A：「内存版是不是完全不能用？」**

> 「不是。它快 139 倍——实测 733,873 次/秒，Redis 单条只有 5,271 次/秒。
>
> 如果只是实时看板的近似计数、允许丢，内存版完全够用，而且更好。我的场景是安全告警，漏报的代价远大于延迟，所以必须放进程外。
>
> **这不是性能优化，是正确性修复。**」

**追问 B：「Redis 挂了怎么办？」**

> 「降级：窗口状态丢了，最多少聚合，但告警不会停——规则匹配和落库还在。
>
> 这是有损降级，不是功能中断。我在设计时就接受这个：宁可粗一点，不能停。」

---

### Q11 讲一个你独立完成的全栈项目

→ 用 3.1.2 的两分钟版，重点讲"模型不碰价格"那个设计。

**追问 A：「前端你写的部分，最难的是什么？」**

> 「**流式**（结果一边生成一边显示，不用等全部算完）的接法。
>
> 一开始我用普通的 fetch，等全部返回才渲染，用户要干等十秒。后来改成 SSE，但会遇到几个坑：结束时要主动关闭连接，不然会挂着；还要区分『正常结束』和『中途出错』——推数据推到一半网关挂了，前端得知道这是失败而不是完成。」

**追问 B：「如果前端要改一个字段名，你要改几个地方？」**

> 「两个：后端的 **Pydantic 模型**（Python 里定义"数据长什么样"的类，字段类型不对会自动报错）和前端 TS 的类型定义。
>
> 但因为前端是 TS，字段名写错编译期就报错，不用等运行时。这就是我选 TS 的原因——把错误提前。」

---

### Q12 前端你用什么状态管理？为什么不用 Redux？

> 「我用 React 自带的 useState / useReducer 加 Context，没引 **Redux**（一个专门管状态的库，要求你写 action、reducer 那一套）。
>
> 原因是这个应用的状态只有一份、更新路径清晰——对话流在走、配置单在变，没有跨页面共享的复杂状态。这种情况引 Redux 是给自己加负担。
>
> 如果状态开始跨模块共享、或者需要时间旅行调试，那就该上了。」

**追问 A：「组件你是怎么拆的？」**

> 「按功能拆：输入区、工具调用过程区、配置单展示区、警告区。
>
> 配置单是纯展示组件——数据从父层传下来，它自己不发请求、不存状态。这样好测也好改，换个地方展示直接复用。」

**追问 B：「不用 Redux，多个组件要读同一个值怎么办？」**

> 「用 Context 把它提升到共同的父层。代价是父层一变，所有消费它的组件都要重渲染。
>
> 我这个应用里这种共享值不多（主要是当前配置单），所以没成问题。如果多到几十个，Context 会带来性能问题，那就该上状态库了。」

---

### Q13 后端接口怎么设计的？

> 「按资源分，不按页面分。比如告警系统就是三张表对应三组接口。
>
> 几个具体决定：
> ① 列表分页不用 **OFFSET** 用**游标**——30 万行的表 OFFSET 20 万要 42 毫秒，游标稳定 3 毫秒；
> ② 错误用 **HTTP 状态码**（三位数字表示结果，2xx 成功、4xx 你这边的问题、5xx 服务端的问题）分语义：参数错 400、找不到 404、服务错 500；
> ③ 写接口考虑**幂等**（同一个操作执行一次和执行一百次，结果一样）——关联表用唯一约束挡重复，事件计数用自增不用赋值。」

**追问 A：「为什么分页不用 OFFSET？」**

> 「因为 OFFSET 的真实含义是"读出来再丢掉"。`OFFSET 200000` 不是"直接跳到第 20 万行"，是"把前 20 万行读出来然后扔掉"。EXPLAIN 里 rows 直接写着 100020。
>
> 游标是 `WHERE id < 上一页最后一个 id`，走索引 range 扫，扫到 20 行就停。
>
> 代价是不能跳页——产品上多数信息流场景不需要跳页，所以这个代价值得。」

**追问 B：「参数校验放前端还是后端？」**

> 「两边都做，但**只信后端**。前端校验是为了用户体验（早点提示），后端校验是为了正确性——前端能被绕过。
>
> 我用 Pydantic 定义模型，字段类型不对、超出范围，直接返回 422，一行校验代码都不用写。」

### Q14 项目部署在哪？怎么部署的？

**追问 B：「为什么用多阶段构建？」**

> 结果镜像小很多——少几百 MB，传输快，攻击面也小。」

### Q16 Node.js 你熟吗？（这家必问，你唯一的真缺口）

> 「Node 我没在生产项目里用过，这点我先说清楚。
>
> 但对我来说它不是新东西：JS 和 TS 我熟，cpAgent 前端整个是我写的。**Node 换的是运行时不是语言**——你写的还是 JS，只是从"浏览器里跑"变成"服务器上跑"。
>
> 它由两块组成：**V8**（Google 的 JS 引擎，就是 Chrome 里跑 JS 的那个，负责执行代码）+ **libuv**（负责事件循环和 I/O 的库）。所谓"单线程"指的是**你的 JS 代码**在一个线程上跑，不是整个程序只有一个线程——真正的读写文件、查数据库这些慢活，交给 libuv 背后的线程池异步做。
>
> 而且我写 FastAPI 用的 `async / await` 和 JS 的 `async / await` 几乎是同一个东西，思维可以直接搬。
>
> 给我两周：第一周把 Express 或 Nest 的路由、中间件、错误处理跑通，第二周照着现有代码写业务模块。」

**追问 A：「Node 为什么适合高并发？」**

> 「**不是因为它快，是因为它不阻塞。**
>
> 一个请求在等数据库的时候，事件循环去处理别的请求了。所以同样一台机器能挂更多并发连接。
>
> 代价是：一个重计算会把整个事件循环卡住——比如你写了个死循环，整个服务就停了。所以它适合 I/O 密集（等网络、等磁盘），不适合 CPU 密集（算图像、算加密）。」

**追问 B：「那 CPU 密集的活怎么办？」**

> 「Node 里有 `worker_threads` 可以开子线程，或者干脆拆成独立服务用别的语言做。
>
> 这也是为什么很多 Node 项目会把重计算下沉到 Python 或 Go 的服务里——Node 做网关和编排，重活交给专门的服。」

> 📌 **这题的答法关键**：先承认没用过（不装），再证明"我理解它的原理"（V8 + 事件循环 + 单线程指的是什么），最后给迁移依据（async/await 同构）和时间承诺（两周）。**三段缺一段都会掉分。**

### Q17 Vue 用过吗？

> 「Vue 我读过文档，没在实际项目里用过，项目里用的是 React。
>
> 两者差在**更新机制**：React 是状态变了触发重新渲染 + 对比差异（diff）；Vue 是靠**响应式**（你改数据，它自己知道哪块界面依赖这个数据，只更新那一块）。
>
> 核心概念——组件、props、状态提升、生命周期——是通的。
>
> 给我一周能改现有页面，两周能独立写新页面。」

**追问 A：「那你更喜欢哪个？」**

> 「用惯了 React。它逼我把状态想清楚——因为你不手动管好状态，重渲染就会出问题。
>
> 但这不是说 Vue 不好。Vue 上手更快，团队里新人多的时候反而合适。**选哪个是团队决定，不是我偏好决定。**」

**追问 B：「React 里列表为什么要加 key？」**

> 「**diff**（对比新旧界面，算出最小更新量）的时候，靠 key 认出"这一项还是原来那一项"。
>
> 不加 key 就按位置比，会导致状态错位——比如你删了第一项，输入框里的文字会跑到第二项上去。性能也会变差，因为它不知道该复用哪个节点。」

### Q18 数据库索引怎么设计的？

> 「**索引按查询建，不按字段建。**
>
> 比如列表页是 `where status = 'open'` 再按 `last_seen` 倒序取 20 条，我就建 `(status, last_seen)` **联合索引**（一个索引包含多列）——等值条件在前、排序字段在后，这样排序直接用索引顺序，**EXPLAIN**（MySQL 里看"这条查询到底怎么执行"的命令）里没有 **filesort**（额外排序，说明索引没用上）。
>
> 原则是明细表只增不改，索引控制在三个以内——每个索引写入时都要维护，还占 **buffer pool**（MySQL 在内存里缓存数据页的区域，索引也要占）。」

**追问 A：「索引什么时候会失效？」**

> 「四种：
> ① 列上做函数或运算——`WHERE DATE(created_at) = '...'` 就用不上；
> ② 隐式类型转换——字段是字符串却传了数字；
> ③ 前导模糊——`LIKE '%关键词'` 以通配符开头，没法走索引；
> ④ OR 连接的列里有一个没索引，整体就退化成全表扫。」

**追问 B：「EXPLAIN 你看哪几列？」**

> 「四列：`type`（访问方式，好到坏是 const > eq_ref > ref > range > index > **ALL**，ALL 是全表扫必须改）、`key`（实际用了哪个索引，NULL 说明没用）、`rows`（预估扫多少行）、`Extra`（有 `Using filesort` 或 `Using temporary` 就要警惕）。
>
> 我最常看 `rows`——它直接告诉你这条查询要扫多少行，最直观。」

### Q19 深分页怎么优化？

> 「**OFFSET** 换**游标**（也叫 keyset 分页）。30 万行的表，OFFSET 20 万要 42 毫秒，改按 id 翻页后稳定 3 毫秒。
>
> 原因是 OFFSET 的真实含义是"读出来再丢掉"——EXPLAIN 里 rows 直接写着 100020。游标是 `WHERE id < 上一页最后一个id`，走 range 扫到 20 行就停。
>
> 代价是不能跳页。所以后台表格用 OFFSET，信息流和日志列表用游标。」

**追问 A：「游标分页遇到数据变动会怎样？」**

> 「反而更稳。OFFSET 分页时如果有人插了新数据，你翻下一页会看到重复的行（因为整体往后挪了）；游标分页是基于具体的 id，不受影响。
>
> 这也是为什么信息流类产品都用游标——用户一直在滚，重复内容体验很差。」

**追问 B：「不能跳页，产品经理非要跳页怎么办？」**

> 「两个办法：一是缓存每页的起始 id，翻页时查缓存；二是接受 OFFSET 的代价，但只在后台管理界面用（那里翻页不频繁，42 毫秒也能接受）。
>
> **关键是分清场景**——不是所有列表都需要同样的分页方案。」

> 💡 这题我踩过一个坑：第一次跑 EXPLAIN 看到 `Impossible WHERE`，以为优化成功，其实是参数算成负数、查询根本没执行。**性能对比前先确认查询真的跑了。**

### Q20 Redis 为什么用 ZSet 不用 INCR 计数？

> 「**INCR**（把某个 key 的值加 1）+ EXPIRE 是**固定窗口**：10:09:59 来 3 条、10:10:01 来 3 条，两个 key 都不足阈值 5，就漏了。真实攻击不按我的窗口边界分布。
>
> **ZSet** 用时间戳做 score，才是真的**滑动窗口**——每次先砍掉窗口外的，再数剩下的。窗口跟着当前时间往前滑，不会在整点重新计数。」

**追问 A：「ZSet 会不会很占内存？」**

> 「每条记录约 60-80 字节，100 万条约 70MB。所以配了 `maxmemory 256MB` + `allkeys-lru`（内存满了按最近最少使用淘汰）。
>
> 而且窗口会自动裁剪——超过 10 分钟的记录每次写入时就被删掉了，不会无限增长。」

**追问 B：「多实例部署时，两个实例各写一个 ZSet 会不会重复计数？」**

> 「不会。ZSet 的 member 用告警 id，天然去重——同一条告警被两个实例写两次，只是覆盖同一个 member 的 score。
>
> 这也是我选 ZSet 而不是自己维护计数器的原因之一：**它天然幂等**。」

### Q21 缓存穿透、击穿、雪崩是什么？

> 「三个都是"缓存挡不住、请求全压到数据库"，区别在触发原因。
>
> **穿透**——查根本不存在的数据，缓存永远不命中 → **缓存空值**（把"不存在"也缓存起来，TTL 给短，比如 60 秒）；
> **击穿**——一个热点 key 刚过期的瞬间，大量请求同时回源 → **加锁**（`SET NX` 抢锁，只放一个请求去查）；
> **雪崩**——大批 key 同一时刻过期 → **TTL 加随机抖动**（把过期时间打散）。
>
> 一句话记：穿透是"本来就没有"，击穿是"刚没有"，雪崩是"一起没有"。」

**追问 A：「那你缓存效果怎么样？」**（诚实答题，很加分）

> 「**只提升 7%**（命中 24.7ms vs 回源 28.1ms）。因为这个量级下主键查一行本来就 1-3ms。
>
> **所以我没把缓存写成优化成果**，只把它定位成给未来慢查询留的接口。写进简历里说"加了缓存提升性能"，被问具体多少就露馅了。」

**追问 B：「缓存和数据库不一致怎么办？」**

> 「用 **Cache Aside**（最常用的缓存模式）：先更新数据库，再删缓存。
>
> 关键为什么是"删"不是"更新"——删是**幂等**的（删一次和删十次结果一样），更新不是。并发下两个更新可能乱序写入，导致缓存里是旧值。
>
> 极端情况仍可能不一致（删缓存失败），所以关键数据我会设较短的 TTL 兜底。」

### Q22 大模型输出不稳定怎么处理？

> 「分两种。
>
> **格式不稳定** → **结构化输出** + 参数校验。字段缺了直接报错重试，不让它半对半错流下去。
> **内容不稳定** → 能算的别让模型算（价格、总价都是算法算的），不能算的要给依据（每个答案要能溯源到条款号，溯不到就拒答）。
>
> 最关键的原则：**架构上不给机会 > 参数上兜住 > 输出上校验。** 只做最后一道是最弱的，那是事后补。」

**追问 A：「怎么判断它答得对不对？」**

> 「三层：能不能溯源（依据有没有）、该不该答（越权/库外要拒）、答得全不全（评测集打分）。
>
> 告警系统里我还加了**轨迹评测**——不只看结论对不对，还看"该查的有没有查"。结论对但过程偷懒，也算不合格。」

**追问 B：「有没有遇到过模型就是不肯按格式输出的情况？」**

> 「有。我的处理是：第一次失败重试并加强格式约束，第二次还不行就走**降级路径**——用规则兜底或者返回"这次没解析出来"。
>
> 最不该做的是"硬解析"——用正则从一段乱七八糟的文本里抠 JSON，抠出来的东西经常是错的，而且错了没人知道。」

### Q23 token 成本怎么控？

> 「**token**（模型处理文本的最小单位，一个汉字大约 1-2 个，API 按它计费）四个办法，按性价比排：
>
> ① **上下文裁剪**——只带相关的历史，不要把整段对话全塞；
> ② **结果缓存**——相同输入复用；
> ③ **能不用模型就不用**——告警降噪那步纯规则，3000 条压到 40 个事件，一次模型没调；
> ④ **先算账再上线**——校规问答的自检环节我 A/B 测过，没有准确率提升、成本反而高 2.2 倍，所以默认关了。」

**追问 A：「缓存会不会导致答案过时？」**

> 「会，所以缓存要设 **TTL**（存活时间，到期自动失效），而且不能对"事实类"内容做长期缓存——价格这种数据一分钟就可能变。
>
> 我的做法是缓存命中后仍做一次时效校验，过期就走完整链路。」

**追问 B：「怎么知道一次会话花了多少钱？」**

> 「我加了一层审计：每次 LLM 调用都落一条记录，包括模型、prompt token、completion token、耗时和折算成本。
>
> 所以我能查任何一次会话、任何一轮的账单。实测一次配置单生成是 4 次调用、约 0.0066 元。」

> 💡 这一条是**加分项**：79% 的企业经历过 AI 成本超支，能说清"我怎么算账"的应届生很少。

### Q24 怎么保证代码质量？

**追问 A：「自己审自己有什么用？不就是走过场吗？」**

**追问 B：「那你怎么保证 AI 生成的代码质量？」**

### Q25 SSE 和 WebSocket 什么区别？

> 「**SSE**（Server-Sent Events，服务器单向往浏览器推）是单向、基于普通 HTTP、浏览器自带重连；**WebSocket**（双向的长连接，握手后双方都能主动发）是双向、独立协议、要自己写心跳。
>
> 我只推不接收，所以用 SSE——省很多代码。如果要做双向交互，比如用户边生成边打断，那就该用 WebSocket。」

**追问 A：「SSE 有什么坑？」**

> 「三个：① 结束时要主动关闭连接，不然会挂着；② 要区分"正常结束"和"中途出错"——推一半网关挂了，前端得知道这是失败；③ 有些代理会缓冲 SSE，导致"看起来没反应"，要配 `X-Accel-Buffering: no`。」

**追问 B：「多用户同时连，后端扛得住吗？」**

> 「SSE 是长连接，每个用户占一个连接。几百个并发没问题，上万个就要考虑连接数上限和内存。
>
> 我的场景是桌面应用单人使用，没这个问题。如果是面向公众的产品，可能要把"生成"和"推送"拆开——生成走队列，推送用专门的网关。」

### Q26 什么是幂等？你项目里用在哪？

> 「同一个操作执行一次和执行一百次，结果一样。像按电梯按钮——按一次和按十次，电梯都只来一趟。
>
> 我用在两个地方：
> ① 关联表用**复合主键**（两个字段一起做主键，这样同一个组合只能出现一次）+ `INSERT IGNORE`（插入时如果冲突就忽略，不报错），同一条告警重复投递不会产生重复行；
> ② 事件计数用 `alert_count + 1` 自增，而不是 `= 5` 赋值，重复执行结果一样。」

**追问 A：「为什么 HTTP 的 GET 是幂等的，POST 不是？」**

> 「GET 只是查询，不改数据，调多少次数据都一样；POST 通常是"新建"，调两次就建两条记录。
>
> 这个区别的实际意义是**能不能安全重试**——网络超时了，GET 可以放心重发，POST 不能，除非接口本身做了幂等设计。」

**追问 B：「那怎么让一个 POST 接口幂等？」**

> 「常见三种：① 业务唯一键 + 唯一约束（重复插入直接失败）；② 客户端生成一个**幂等键**（每次请求带一个唯一 id），服务端用 Redis 记一下"这个 id 处理过了"，重复的直接返回上次结果；③ 乐观锁（带版本号，版本对不上就拒绝）。」

---

### Q27 你怎么理解"AI 能力的工程化落地"？（JD 原话，必答）

> 「我理解是四件事：
>
> **接口化**——能被别的系统调用，不是一个跑完就完的脚本；
> **稳定化**——超时、返回垃圾、上游挂了，都要有预案（重试、熔断、降级）；
> **可观测**——出了问题能定位，包括"为什么给出这个答案"；
> **可维护**——别人能接手，有测试有文档。
>
> 我的四个例子正好对上：**LLM 可插拔**（接口层，DeepSeek / 本地 Ollama / Mock 一个开关切换）、**三道闸 + 三态熔断**（稳定层）、**轨迹评测**（可观测层）、**27 单测 + CI 六关**（可维护层）。」

**追问 A：「什么是"三态熔断"？」**

> 「**熔断**是下游一直失败时主动停止调用，别让请求堆积把整个系统拖死——像保险丝过载就断。
>
> 三个状态：**关闭**（正常调用）、**打开**（直接失败，不再尝试）、**半开**（放一个请求去试，成功就恢复，失败继续断）。
>
> 为什么要半开：一直不开就永远用不了；一直试又会把还没好的下游再打死。半开是折中，而且**只放一个探针**——放一批会把刚起来的服务再压垮。」

**追问 B：「LLM 可插拔具体怎么做的？」**

> 「定义一个统一的接口（Python 里就是个抽象基类），规定必须有 `chat()` 方法；每个 provider 实现它。
>
> 好处是：换模型改一行配置；测试时用 **Mock**（假的替代品，永远返回预设答案，这样测试不花钱、不受网络影响）；本地开发用 Ollama，线上用 DeepSeek，代码不用动。」

# 第五部分：如何用 AI 辅助开发（完整可复述）

> 这是现在企业很看重的一块。答不好会被认为"没 AI 就不会写"，答得太依赖会被认为"不是自己想出来的"。
> **核心是讲清边界：哪些交给它、哪些不交、怎么验证。**

## 5.1 一句话立场（开场就说这句）

> **「我用 AI 做执行，不用 AI 做判断。」**
>
> 「它能帮我把一个模型层从两小时压到二十分钟，但架构怎么分层、这个取舍该不该做、结果对不对，都是我自己定的。」

## 5.2 四个用、三个不用

**交给 AI 的四件事**：
1. **样板代码**——Pydantic 模型、CRUD 路由、序列化
2. **查不熟的库**——某个 API 签名、某个配置项
3. **报错定位**——把 traceback 给它，让它判断可能原因
4. **初稿**——测试用例清单、文档骨架

**不交给 AI 的三件事**：
1. **架构决策**——选型、模块划分、数据放哪
2. **取舍判断**——该不该做、值不值
3. **验收标准**——怎么算"做对了"

> 「后三样一旦错了，后面所有代码都要重写。」

## 5.3 三层验证

> **能跑 → 能讲 → 能扛**

- **能跑**：跑一遍看结果对不对（最低要求，但"能跑"和"跑对"是两件事）
- **能讲**：**每一行都要能解释为什么这么写，讲不出来的就重写**（讲不出来 = 不理解 = 出问题不敢改 = 这段代码成了黑盒）
- **能扛**：边界条件、异常输入、并发（AI 生成的代码通常只覆盖顺利路径）

**四个具体做法**：
1. 先让它说思路，我看思路对不对，再看代码
2. 一次只让它改一个函数（大段生成必出错，且定位困难）
3. 关键逻辑我自己写（钱、权限、状态机）
4. 要求它同时给测试（没测试的生成代码等于没验收）

## 5.4 三个真实案例（这段最有说服力）

**案例一：凭印象写错工具名**

> 「做工具风险分级时，我按印象写了 `refresh_price`，实际代码里叫 `refresh_prices`。后果是那个**会写数据库的工具没被降级**，风险等级还是"只读"，意味着能被 Agent 自主执行。
>
> 靠打印全量工具清单核对才发现。**AI 生成的配置表看起来完全合理，但它不知道你代码里实际叫什么。**」

**案例二：四个不同的 CPU 被算成同一个价**

> 「让 AI 写型号匹配逻辑，它给的是词元重叠度打分。结果 9950X3D、9900X3D、9800X3D、7800X3D 这四个型号，价格全被算成 2199。
>
> 为什么错：这四个名字里都有 `amd ryzen` 和 `x3d`，重叠度都很高，全被匹配到列表里第一个 x3d 产品。
>
> **怎么发现的？不是靠读代码——代码逻辑看起来没问题。是靠常识：这四个 CPU 差价好几千，不可能同价。**」

**案例三：差点用错价格源**

> 「项目自带的刷新脚本跑完，RTX 4080 Super 从 8499 变成 25681。还是靠常识发现的——一张 4080 不可能两万五。
>
> 查下去才看到，那个脚本的数据源是美元街价（含 eBay 二手）和 Amazon UK 含税英镑价，海外价，比国内高 1.5-3 倍。」

**共同点（这句是重点）**：

> **「没有一个是靠读代码发现的，全是靠"我知道正常应该是什么样"发现的。**
>
> **所以我的结论是：AI 的产出要用领域知识去验，不是用代码能力去验。」**

## 5.5 五条原则（被追问就报这五条）

1. 先想清楚再让它写——想不清就不写
2. 一次只改一个函数——大段生成必出错
3. 关键逻辑自己写——钱、权限、状态机不生成
4. 它给的每个数都要核——数字比逻辑更容易错得隐蔽
5. 讲不出来的代码就重写——不理解 = 不该留

## 5.6 六个追问

**「没有 AI 你还能写吗？」**
> 「能，但要慢很多。关键逻辑本来就是我手写的——配置单的确定性拼装、Redis 窗口的裁剪逻辑、风险分级那道闸。AI 省的是样板和查文档的时间。」

**追问：「你说关键逻辑自己写，那哪些算关键？」**
> 「三类：涉及钱的（价格计算）、涉及权限的（谁能做什么）、涉及状态的（状态机怎么流转）。
>
> 这三类错了后果最重，而且最难通过测试发现——测试只能测你想到的情况。」

**「怎么证明这些是你写的？」**
> 「您可以随便挑一个函数问我。我能讲清为什么这么写、放弃了什么方案。
>
> 比如那段确定性拼装，我第一版是让模型直接输出整张配置单，跑五次给五个不同结果，才改成算法拼装——这个过程 AI 给不了我。」

**「AI 写的代码质量怎么保证？」**
> 「三层：能跑、能讲、能扛。加上单测和 CI 门禁。」

**「你会不会过度依赖？」**
> 「我有明确的'不用 AI'清单——架构、取舍、验收标准这三样不交给它。而且我会定期做一件事：把 AI 写的代码关掉重写一遍，看能不能写出来。」

**「AI 帮你省了多少时间？」**
> 「样板代码能省 80% 左右（两小时压到二十分钟）。但省下来的时间大部分又花在验证上了。」
>
> ⚠️ **别吹**。说"省了十倍"反而不可信。诚实说"省执行时间，但验证成本上升"更让人信服。

**「你怎么判断 AI 说的对不对？」**
> 「用领域常识判断，不用代码能力判断。刚才那三个坑，全是靠'这个价格不合理''这四个不该同价'发现的。」

## 5.7 一个加分动作（视情况提）

> 「如果您想看，可以现在打开项目，随便挑一段代码让我讲。或者挑一个函数让 AI 解释一遍，我告诉您它哪里说得不准确。」

**敢说这句话的人通常真懂。但要先确认自己每块都讲得清——别挖坑。**

# 附录：项目完全理解自检表

> 用法：**盖住右边，只看左边的技术点，能不能用一句话说清 + 说出为什么这么做。** 说不出来的回去补。

## A. cpAgent 自检（12 项）

| 技术点 | 我能不能说清 |
|---|---|
| ReAct 循环怎么跑的 | 想一步 → 调工具 → 看结果 → 再想，最多 12 步；工具白名单限制能调什么 |
| 为什么最多 12 步 | 实测 12 步够覆盖正常需求，超了说明在绕圈，中断比烧 token 好 |
| 配置单为什么不是模型生成 | 模型会编型号、会算错价；改成算法拼装后它想编也没地方编 |
| 确定性注入是什么 | 预算/用途以工作记忆为准，模型填什么都覆盖——因为模型对数字不敏感 |
| 三道闸是哪三道 | 步数上限 / token 预算 / 重复调用检测 |
| SSE 怎么用的 | 后端 StreamingResponse + `text/event-stream`，前端 EventSource 或 fetch 流式读 |
| MCP 是什么、你怎么做的 | 一个统一接工具的协议，类比 USB；你写了 stdio 的 MCP Server 暴露三个工具 |
| 证据链怎么工作 | 工具原始返回落 SQLite，回复里每个价格要能回溯，回溯不到标幻觉风险 |
| 审计记了什么 | 每次 LLM 调用的模型/token/成本/耗时 + 每个高风险动作的审批决定 |
| 风险三档怎么分 | read 直接跑 / write_reversible 跑完留痕 / write_irreversible 挂起等人批 |
| 为什么不靠提示词做约束 | 提示词是"求它别错"，代码是"它没机会错" |
| 价格来源怎么标注 | 每条带 price_source + fetched_at + confidence，过期的标 expired，估算价进 warnings |

## B. 告警系统自检（10 项）

| 技术点 | 我能不能说清 |
|---|---|
| 四层链路 | 聚合 → 富化 → 研判 → 决策 |
| 指纹怎么算 | sha1(IP + 规则号) 取前 32 位；定长、索引紧凑、key 短 |
| 为什么 10 分钟窗 | 大部分自动化扫描集中在 10 分钟内；太大会合并相邻事件，太小会切碎 |
| 降噪率怎么来的 | (3000−40)/3000；**纯规则，不调模型** |
| 三档路由 | 高置信自动关 / 中置信抽检 / 低置信（<0.8）转人工 |
| 为什么用 ZSet | INCR+EXPIRE 是固定窗口会漏；ZSet 用时间戳做 score 才是真滑动窗口 |
| 重启实验证明了什么 | 内存版 3 条重启后归零、再灌 2 条凑不到 5 → 攻击漏报 |
| 深分页怎么优化的 | OFFSET 42ms → 游标 3ms；代价是不能跳页 |
| 六个索引服务哪些查询 | 时间范围、同指纹窗口计数、按规则统计、列表页排序、更新定位、关系反查 |
| CI 六关是哪六关 | lint / 单测 / 构建 / 安全扫描 / 镜像构建 / **评测门槛** |

## C. 校规问答自检（8 项）

| 技术点 | 我能不能说清 |
|---|---|
| 四段链路 | 查询改写 → 依据原文作答 → 自检分流 → 多轮记忆 |
| 为什么需要查询改写 | 用户用口语问，制度用书面语写，不改写检索命中率低 |
| 怎么保证不胡说 | 必须命中原文 + 必须带条款号 + 越权/库外必须拒答 |
| 评测集怎么设计的 | 25 条，含 4 类陷阱题（越权、库外、违规、常识） |
| 调参调了什么 | top_k 从 3 调到 8，召回从漏到 21/21 |
| A/B 测出什么 | 自检环节没有准确率提升、成本高 2.2 倍 → 默认关闭 |

## D. 如果被要求画架构图，你画什么

按这个顺序画，边说边画：

```
用户输入
   ↓
[偏好提取] → 工作记忆（预算/用途/分辨率）
   ↓
[ReAct 循环] ──→ 工具层（查库 / 搜价 / 抓网页）
   ↓              ↓
   ↓          [证据库] 原始返回落盘
   ↓
[确定性拼装] ← 硬件库
   ↓
[兼容性校验] → 输出
```

**边画边说这三句**：
1. 「模型只在循环里做决策，不碰具体数据」
2. 「工具返回的东西全部落证据库，后面要能追溯」
3. 「配置单是在循环外面由算法拼的，这是刻意的」

## E. 如果被要求现场演示，你演示什么
