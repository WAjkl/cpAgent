# 决策卡：吃透项目就不用背题

> 你的想法：**"如果真的理解了项目，是不是就不用背那么多了？"**
>
> 客观回答：**对，但只对一半。** 这一半对了能省 80% 的力气，另一半错了会在追问环节崩。

---

# 第一部分：客观分析

## 1.1 你的判断哪里对（这半是对的，而且很关键）

**① 背题有个致命缺陷：第 44 个问题就崩**

背了 43 题，面试官问一个没准备的，照样哑。**而理解的人能从原理推出来。**

**② 理解的人答得更生动**

背题的答案只有骨架，听起来像复述；理解的答案会自然带出细节、取舍、踩过的坑——**而这些恰恰是加分项**。

**③ 最关键的：理解 = 有能力现场生成答案**

这是真正的区别：
- 背题 = 从记忆里**检索**答案
- 理解 = 现场**生成**答案

**面试官问的问题几乎不可能和你准备的一模一样。所以"生成能力"比"检索能力"重要得多。**

## 1.2 但你的判断有一个盲区

**"理解项目" ≠ "能讲清决策"。这是两件事。**

面试官问的 90% 不是"你怎么实现的"，而是"**你为什么这么选**"。

| 问题类型 | 频率 | 靠什么答 |
|---|---|---|
| "你这个功能怎么实现的" | 低 | 理解代码就够 |
| "**为什么这么设计**" | **高** | **要理解取舍** |
| "如果换个场景还适用吗" | 中 | 要理解边界 |

**举个你的例子**：

你知道 `agent_loop.py` 里写了 `max_steps = 12`——这叫**理解实现**。

但如果面试官问「**为什么是 12，不是 20 或 8**」，你只理解"代码里写了 12"是答不上的。要答得上，你得知道：
- 实测正常需求几步够
- 超过多少步说明在绕圈
- 调高会烧多少 token

**这才是"讲清决策"。**

## 1.3 还有一个更隐蔽的盲区

**理解 ≠ 能表达。**

三件不同的事：
1. **理解**——我知道我的代码怎么跑
2. **能讲清**——我能把理解组织成对方听得懂的话
3. **讲得好**——我知道什么先说、什么省略、怎么收尾

很多人**理解但讲不出来**——脑子里有，嘴上卡。尤其被追问时。

**所以"理解"能替代"背答案内容"，但替代不了"练表达"。**

# 第二部分：所以真正该做的

## 2.1 关键转换：从"背 43 题"改成"吃透 10 个决策"

**为什么可以这么做？**

因为**43 个问题里，大部分是同一批决策的不同问法。**

比如「为什么不让模型算价格」这一个决策，能回答至少 6 个问题：
- 你怎么防幻觉？
- 你的架构为什么这么分层？
- 模型在你的系统里负责什么？
- 你怎么保证结果可复现？
- 模型不听话怎么办？
- 你的 Agent 和别人的有什么区别？

**一个决策 → 六个答案。这就是为什么吃透决策比背题高效。**

## 2.2 决策卡片法

每张卡四样东西：

| 项 | 内容 |
|---|---|
| **① 我选了什么** | 一句话说清结论 |
| **② 为什么这么选** | 对比了哪些方案，为什么淘汰它们 |
| **③ 代价是什么** | 我为此付出了什么 |
| **④ 重来会改吗** | 复盘 |

**有了这四样，任何问法都能答。**

# 第三部分：你的 10 张决策卡

> 下面是我从你三个项目里提炼的 10 个**真正的决策点**。每张卡后面标了"能覆盖哪些常见题"。

---

## 卡 1｜配置单不让模型拼，改成算法拼

**① 选了什么**：模型只输出参数（预算/用途/档次判断），配置单由确定性算法从硬件库拼装。**模型的输出里没有价格字段。**

**② 为什么**：第一版我让模型直接输出整张配置单 JSON，跑五次给五个不同结果，有时 8000 预算配出 9200，理由是"觉得可以超一点"。我一开始想靠提示词约束（加"严格不要超过预算"），**没用**。后来想明白：这不是提示词的问题，是架构的问题。

**③ 代价**：灵活性下降。模型能"自由发挥"配出一些奇怪但可能合理的组合，现在被算法约束住了。换来的是可复现和可解释。

**④ 重来会改吗**：不会。而且这个思路我迁移到了别处——**任何"模型不该碰的关键值"（金额、权限、库存）都应从模型输出里拿掉。**

**能覆盖的题**：你怎么防幻觉 / 架构为什么这么分层 / 模型负责什么 / 怎么保证可复现 / Agent 和别人的区别 / 结果不稳定怎么办

---

## 卡 2｜步数上限设 12

**① 选了什么**：ReAct 循环最多 12 步，超了中断并给保守回答。

**② 为什么**：实测正常需求 5-8 步就够（提取偏好 → 查 2-3 次库 → 生成配置 → 校验 → 回答）。12 步留了余量，但如果超过 12 步，基本说明它在绕圈——**这时候继续只会烧 token，不会变对**。

**③ 代价**：少数复杂需求（比如要多轮澄清）可能被截断。

**④ 重来会改吗**：不会改数值，但会改**中断后的行为**——现在只是中断，更好的做法是"中断时告知用户缺什么"，而不是硬给一个答案。

**能覆盖的题**：为什么 12 步 / 循环调不停怎么排查（这是排查的第一步依据）/ 怎么控制成本 / 三道闸是什么

---

## 卡 3｜上下文只放摘要，不放工具原文

**① 选了什么**：工具返回的原始结果完整落库（evidence），但进模型的上下文只放**摘要**。

**② 为什么**：查一次硬件库可能返回 20 条带完整规格的记录，占几千 token。而模型决策只需要知道"有哪些型号、什么价位"。**摘要能省 80% token。**

**③ 代价（这是最重要的部分）**：**摘要可能丢关键信息**，导致模型以为"没查到"而重复查询。这是我设计里的一个真实风险点——如果摘要写得太狠，模型会误判。

**④ 重来会改吗**：会。**摘要要保留"有没有结果"这个信号**（比如明确写"查到 20 条，以下是前 5 条"），而不是只给 5 条——否则模型不知道还有 15 条。

**能覆盖的题**：怎么控成本 / Agent 循环调不停（这是排查方向二）/ 摘要压缩的风险 / 长对话怎么处理

---

## 卡 4｜三个 SQLite 库分开

**① 选了什么**：evidence（证据）/ longterm_memory（记忆）/ audit（审计）三个独立库，不是一个库三张表。

**② 为什么**：三者读写模式完全不同——
- 证据是**大字段、只追加、按会话整批取**（raw_result 可能几 KB）
- 记忆是**小字段、读多写少、按用户找**
- 审计是**高频追加、要 GROUP BY 聚合**

**混在一张表里，索引会互相打架**；SQLite 一页 4KB，大字段还会把热点数据挤出缓存。

**③ 代价**：跨库查询麻烦（比如"这个会话的所有证据+成本"要查两次再合并）。事务不能跨库。

**④ 重来会改吗**：不会。但会加归档机制——现在没有 TTL，数据会一直涨。

**能覆盖的题**：存储怎么设计 / 为什么不用 MySQL / 查询场景 / 写入压力 / 审计怎么做 / 数据会一直涨吗

---

## 卡 5｜LLM 做成可插拔

**① 选了什么**：抽象基类 + 三个实现（DeepSeek / Ollama / Mock），配置切换。

**② 为什么**：
- **换模型是一年内必然发生的事**（价格、能力、可用性都在变）
- **测试需要 Mock**（不然每次跑测试都花钱、都依赖网络）
- **本地开发用 Ollama**（不烧钱、离线可用）

**③ 代价**：抽象层会削掉各家的特殊能力（比如 DeepSeek 的某些特有参数传不进去）。

**④ 重来会改吗**：不会。但会加一个"能力声明"机制——每个 provider 声明自己支持哪些特性，让上层能判断。

**能覆盖的题**：可插拔怎么设计 / 新增模型改哪些代码 / 怎么测试 AI 功能 / 模型选型 / 成本和稳定性

---

## 卡 6｜工具白名单 + 风险三档

**① 选了什么**：两层——① 只有注册过的工具能被调用（白名单）；② 每个工具标风险级（read / 可逆写 / 不可逆写），不可逆的挂起等人工批准。

**② 为什么**：白名单挡的是"模型幻想出不存在的工具"；风险分级挡的是"模型调了不该自主执行的动作"。

**第二层是关键的**：Demo 里"能自动完成"是卖点，生产环境里"自动完成了不该做的"是事故。而且**这层必须是代码约束，不能靠提示词**——模型输出一次错误的 action，钱就花出去了。

**③ 代价**：不可逆动作要人工介入，牺牲了自动化程度。

**④ 重来会改吗**：不会。但如果要多用户，白名单要从"写死配置"改成"工具-角色-权限"三张表。

**能覆盖的题**：工具权限怎么限制 / 白名单怎么实现 / 多用户怎么改 / Agent 安全边界 / 为什么要人工确认

---

## 卡 7｜工具原始返回完整落库（证据链）

**① 选了什么**：每次工具调用的**原始返回**整段落 SQLite，回复里的价格要能回溯到证据。

**② 为什么**：两个原因——
- **能查**：用户说"这个价格不对"时，能翻出当时的原始返回对账
- **能验**：从回复里提取价格数字，逐个查证据，查不到来源的标幻觉风险

**③ 代价**：存储增长快（每条可能几 KB），而且写库有开销。

**④ 重来会改吗**：不会，但会加冷热分离。

**能覆盖的题**：怎么防幻觉 / 怎么溯源 / 用户投诉价格不对怎么查 / 存储怎么设计 / 审计怎么做

> 📌 **这张卡是全场最有用的**——因为"日志对但结果错"那种题，答案就是"我存了原文才能查"。

---

## 卡 8｜审计记账，单价可配置

**① 选了什么**：每次 LLM 调用落一行（模型/token/成本/耗时/成败），单价做成配置项。

**② 为什么**：
- 企业最怕的不是模型不聪明，是**调用不可见**——花了多少钱、谁花的、为什么这么贵，全说不清
- **单价必须可配置**：模型价格会变，写死的话历史账目就对不上（今天的账按今天的价，以前的账要按当时的价）

**③ 代价**：每次调用多一次写库；而且 token 估算有误差。

**④ 重来会改吗**：不会。会加"预估 vs 实际"双记录。

**能覆盖的题**：成本怎么控 / token 怎么算 / 为什么要审计 / 企业级和 demo 的区别 / 可观测怎么做

---

## 卡 9｜聚合用规则不用模型（AlarmStore）

**① 选了什么**：告警降噪用指纹+时间窗聚合（纯规则），只有"判断是不是真攻击"才用模型。

**② 为什么**：
- 聚合是**确定性任务**——同一批告警永远聚成同样的事件，用模型既慢又不稳
- 而且**规则可解释**：能说清"这两条为什么被合并了"，模型说不清
- 更重要：**98.7% 的降噪率是规则的功劳，我不拿它当模型效果讲**

**③ 代价**：换 IP 打同一台机器会被拆成多簇（纯指纹的固有缺陷）。

**④ 重来会改吗**：不会。但这个"按确定性分工"的思路我迁移到了 cpAgent（算法拼装 vs 模型解释）。

**能覆盖的题**：降噪率怎么算 / 为什么不用模型做聚合 / 规则和模型怎么分工 / 可解释性 / 同一套思路用在两个项目

---

## 卡 10｜窗口状态从内存迁 Redis（AlarmStore）

**① 选了什么**：滑动窗口状态从进程内存迁到 Redis ZSet。

**② 为什么**：内存版有两个硬伤——**重启就丢、多实例各数各的**。

我做了个实验证明：灌 3 条同指纹告警、重启服务、再灌 2 条。内存版计数从 3 归零只剩 2，**永远凑不到阈值 5，这次攻击就漏了**。

为什么用 ZSet 不用 INCR：INCR+EXPIRE 是固定窗口（10:09:59 来 3 条、10:10:01 来 3 条，两个 key 都不足 5 就漏），ZSet 用时间戳做 score 才是真滑动窗口。

**③ 代价**：性能掉了 139 倍（733,873 次/秒 → 5,271 次/秒）。但这是**正确性换性能**，不是优化。

**④ 重来会改吗**：不会。而且这个判断标准我后来一直在用——**这份数据丢了会怎样？**

**能覆盖的题**：为什么迁 Redis / ZSet vs INCR / 性能和正确性怎么权衡 / 重启丢数据 / 多实例 / 深分页怎么优化（同一套实验思维）

# 第五部分：怎么"吃透"而不是"背"

## 5.1 每张卡的自测题（不用背，回答这三个问题）

对每张卡，合上文档问自己：

1. **我选了什么？**（能不能一句话说清）
2. **不这么选会怎样？**（有没有对比方案）
3. **我付出了什么代价？**（能不能说出缺点）

**三个都答得上，这张卡就吃透了。**

## 5.2 一个更狠的验证法

**找个人（同学、家人、甚至对着手机录音）用一句话问他："你这个为什么这么做？"**

如果他能顺着问第二句「那这样不会……吗」，而你能接住——**说明你真懂了。**

**接不住的地方，就是没吃透的地方。**

## 5.3 为什么这比背题有效

| | 背题 | 吃透决策 |
|---|---|---|
| 准备量 | 43 题 | 10 张卡 |
| 遇到新问题 | 崩 | 能推 |
| 追问 | 一深就断 | 越问越显得懂 |
| 答案质感 | 像复述 | 像在讲自己的东西 |
| 遗忘速度 | 快（没逻辑支撑） | 慢（有因果链） |

# 第六部分：客观说，还有哪些必须背

**别指望全靠理解。这三块必须准备：**

| 必须准备 | 为什么理解替代不了 |
|---|---|
| **自我介绍** | 这是表达题，不是知识题。要练到顺口 |
| **公司了解** | 这是外部信息，你的项目里没有 |
| **反问的三个问题** | 这是准备题，临场想不出来 |

**这三块加起来不到 1500 字，半小时能拿下。**

其它（技术题、项目题、缺点）都可以靠"吃透决策 + 练表达"解决。

# 最后：一个判断标准

**面试前问自己一句：**

> **如果面试官问一个我完全没准备的问题，我能用我的项目经验答出来吗？**

- 能 → 你吃透了，可以少背
- 不能 → 说明还是"记答案"的状态，得回去看决策卡

**这就是"理解"和"背题"的分界线。**
