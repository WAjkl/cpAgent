## 1｜let、const、var 的区别

**概念**

| | 作用域 | 变量提升 | 重复声明 | 可重新赋值 |
|---|---|---|---|---|
| `var` | 函数作用域 | 会（值是 undefined） | 可以 | 可以 |
| `let` | 块级作用域 | 有提升但**暂时性死区** | 不可以 | 可以 |
| `const` | 块级作用域 | 同上 | 不可以 | **不可以** |

**关键的一层**：`const` 保证的是**绑定不可变**，不是值不可变。

```js
const a = { x: 1 }
a.x = 2        // ✅ 可以，改的是对象内容
a = { x: 2 }   // ❌ 报错，改的是绑定
```

**挂到你的项目**

你的状态更新全是这个模式：

```ts
conversations: s.conversations.map((c) =>
  c.id === activeId
    ? { ...c, messages: [...c.messages, userMsg, assistantMsg], updatedAt: Date.now() }
    : c
)
```

**这是「用不可变的方式改状态」**——不是 `c.messages.push()`，而是造一个新对象、新数组。
因为 React 判断「要不要重渲染」靠的是**引用有没有变**，你 push 之后引用没变，React 认为没变化，就不渲染了。

**怎么说出口**

> 「var 是函数作用域、会提升、能重复声明；let 是块级作用域，有暂时性死区；const 也是块级，但**不能重新赋值**——注意对象内容能改，只是不能换指向。
>
> 我项目里基本只用 const，因为**状态全是不可变更新的**。React 靠引用判断要不要重渲染，所以我不 push，都是造新数组新对象，引用一变它才知道该渲染。」

**追问｜「那 const 声明的对象能改内容，不是矛盾吗？」**
> 不矛盾。const 锁的是「这个变量指向哪」，不是「这个对象长什么样」。**要保持内容也不可变，得用 `Object.freeze`。**

## 2｜闭包是什么 ★ 最值钱的一题

**概念**

函数 + 它被定义时的词法作用域 = 闭包。

即使外层函数已经执行完毕，内层函数仍然能访问外层函数的变量，因为这些变量被保留在内存里，不随外层调用栈销毁。

**三个典型用途**：私有变量、回调保存状态、函数工厂。

**代价**：被闭包引用的变量不会被回收。如果闭包长期存在（比如挂在事件监听上没解绑），就会内存泄漏。

**挂到你的项目**

这是你最真实的闭包应用，在 `chatStore.ts` 的 `sendMessage` 里：

```ts
const assistantMsg: Message = { id: uid('m-'), role: 'assistant', content: '', status: 'streaming', ... }

const handlers = {
  onDelta: (d: string) =>
    set((s) => ({ conversations: patchMessage(s, activeId, assistantMsg.id, { content: ... + d }) })),
  onConfig: (cfg) => set(...patchMessage(s, activeId, assistantMsg.id, { config: cfg })),
  onDone: () => set(...patchMessage(s, activeId, assistantMsg.id, { status: 'done' }))
}
```

**`handlers` 就是闭包**——它捕获了 `activeId` 和 `assistantMsg.id` 这两个变量。等 SSE 流真正开始吐数据的时候，`sendMessage` 早就执行完了，但这两个值还在，因为闭包把它们留住了。

**为什么这个设计是对的**：每条流的回调都记着**自己的**会话 id 和消息 id。所以用户切到别的会话，旧流还在往原来那条消息写，**不会写到新会话里**。

如果不用闭包，就得用全局变量存「当前正在流式的消息 id」——多会话并发时立刻串。

**怎么说出口**

> 「闭包就是函数记住了它定义时的作用域，外层函数执行完了还能访问外层变量。常见用途是私有变量和回调保存状态，代价是变量不回收，滥用会内存泄漏。
>
> **我项目里流式的回调就是闭包。** 每次发消息我定义一个 onDelta，它捕获了这次请求的会话 id 和这条消息的 id。等流真正吐数据的时候，发消息那个函数早就返回了，但这两个 id 还在，因为闭包留住了。
>
> **所以多会话并发不会串**——每条流的回调记着自己的 id，切会话的时候旧流还在往原来那条消息写。
>
> 反过来说，如果我用一个全局变量存「当前流式的消息 id」，切一下会话立刻串。**闭包在这里不只是语法，是隔离机制。**」

**追问｜「闭包造成内存泄漏怎么避免？」**
> 关键是**及时解绑**。比如事件监听，组件卸载时要 remove。我的流式回调如果请求异常中断没走到结束，这个闭包会一直挂着——所以我加了错误处理，保证每条流无论成功失败都会把状态收口，不然内存会慢慢涨。

**追问｜「for 循环里 setTimeout 打印都是最后一个值，为什么？」**
> 因为 var 是函数作用域，三个 setTimeout 共享同一个 i，等它们执行时 i 已经是 3 了。**换成 let 就好了**，let 是块级作用域，每次循环产生一个新的绑定。

## 3｜Promise 和 async/await 的关系

**概念**

`async/await` 是 Promise 的**语法糖**，本质完全一样。

- `async` 函数一定返回 Promise，返回值会被自动包一层
- `await` 后面必须是 Promise（或值），它会把后面的代码挂起，等 Promise resolve 再继续
- **`await` 只能在 async 函数里用**

错误处理：

```js
// Promise 风格
fetchData().then(r => ...).catch(e => ...)

// async 风格
try { const r = await fetchData() } catch (e) { ... }
```

**挂到你的项目**

你的 `chatSSE` 就是个 async 函数，内部是 `await reader.read()` 的循环：

```ts
for (;;) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })
  ...
}
```

**这里 async/await 的价值很具体**：如果不用 await，你在 `read()` 还没返回的时候就去切 buffer，拿到的永远是空或者半截。**await 保证了「拿到这一块之后才处理这一块」。**

而且你调用方也用 try/catch 包住了整条流：

```ts
try {
  if (alive) await chatSSE(...)
  else await chatMock(...)
} catch (e) {
  // 把消息状态改成 error
}
```

**一个细节**：`try/catch` 能捕获到 `await` 里的 reject，但**捕获不到没 await 的 Promise**——所以流式里每个 await 都在 try 里，是有意的。

**怎么说出口**

> 「async/await 是 Promise 的语法糖，本质一样。async 函数返回的一定是 Promise，await 后面接 Promise，等它 resolve 再往下走。
>
> **我项目里流式解析就是拿它保证顺序的。** 我要循环 `await reader.read()`，拿到一块才处理一块——如果不 await，read 还没返回我就去切 buffer，拿到的永远是半截。
>
> 错误处理用 try/catch 包住整条流，比 .catch() 好读，而且能让每一层的错误都落到同一个地方。」

**追问｜「多个请求想并发怎么办？await 一个个写不就串行了？」**
> 用 `Promise.all`。一个个 await 是串行，`Promise.all([a(), b()])` 是并发，总耗时等于最慢那个。**但要注意：Promise.all 只要有一个 reject 就整体 reject**，想拿到部分成功的结果要用 `Promise.allSettled`。

## 4｜事件循环，宏任务和微任务

**概念**

JS 是单线程，靠事件循环调度。一轮的执行顺序：

1. 执行同步代码（当前调用栈清空）
2. **清空所有微任务队列**（`Promise.then`、`queueMicrotask`、`MutationObserver`）
3. 取**一个**宏任务执行（`setTimeout`、`setInterval`、IO、UI 渲染）
4. 回到第 2 步，循环

**所以**：`Promise.then` 永远比 `setTimeout(fn, 0)` 先执行，即使 setTimeout 写在前面的代码里。

**挂到你的项目**

两个地方能用上：

**① 流式渲染的批量更新**

你每收到一个 delta 就 `set(...)` 一次。React 18 有**自动批处理**——同一个微任务里连续 setState 会合并成一次渲染。所以几百个 delta 不会触发几百次重渲染。

**但这也意味着**：如果你在一个 await 之后、下一个 await 之前连续 set，它们会被合并；跨了 await 就是不同的微任务，会分开渲染。

**② 你后端那个 `await asyncio.sleep(0.015)`**

这个不是 JS 的事件循环，是 Python 的 asyncio 事件循环，但概念是同一个：**让出控制权，别阻塞**。如果不 sleep 直接 yield，分片会瞬间全吐出去，前端的打字机效果就没了。

**怎么说出口**

> 「JS 单线程，靠事件循环调度。同步代码走完，先清空**所有微任务**，再取**一个宏任务**，然后再清微任务，循环。所以 Promise.then 一定比 setTimeout 先执行。
>
> **我项目里跟这个有关的是流式渲染。** 每收到一个 delta 我就 setState，但 React 18 有自动批处理，同一个微任务里的连续更新会合并成一次渲染，所以不会每个字都触发一次重渲染。」

**追问｜「那如果我想强制同步拿到最新 DOM 呢？」**
> 用 `flushSync`，但这会破坏批处理、掉帧，一般不用。正常做法是在 `useEffect` 里拿——那时候 DOM 已经更新完了。

## 5｜TS 里 interface 和 type 的区别 ★ 第二值钱

**概念**

| | interface | type |
|---|---|---|
| 描述对象 | ✅ | ✅ |
| 联合类型 `A \| B` | ❌ | ✅ |
| 交叉类型 `A & B` | 用 extends 代替 | ✅ |
| 声明合并 | ✅ 同名自动合并 | ❌ 重名报错 |
| 实现类 | `implements` | 也可以 |
| 映射类型 / 条件类型 | ❌ | ✅ |

**一句话选法**：描述对象形状用 `interface`，需要组合/联合/工具类型用 `type`。

**挂到你的项目**（这题你有最好的素材）

你的 `api.ts` 里定义了 SSE 事件类型：

```ts
export type ChatEvent =
  | { type: 'status'; session_id: string; routing: unknown }
  | { type: 'delta'; text: string }
  | { type: 'config'; config: Config }
  | { type: 'done'; session_id: string; turn_id: string; evidence_ids: string[]; timeout: boolean }
  | { type: 'warn'; text: string }
```

**这个用 interface 写不出来**——`interface` 只能描述一个形状，不能表达「五个形状中的任意一个」。

而且它是**可辨识联合（discriminated union）**：每种都有 `type` 这个字面量字段。所以你在 `switch (evt.type)` 之后，TypeScript 会自动把 `evt` 收窄成对应那一支——你写 `evt.text` 的时候，编译器知道这一定是 delta 事件，不会报错。

**同一个文件里也有 interface**：

```ts
export interface Config {
  id: string
  total_price: number
  parts: { cpu: PartInfo; gpu: PartInfo; ... }
  ...
}
```

`Config` 是纯对象形状，用 interface 合适。

**所以你项目里两种都用对了**，这是可以讲的。

**怎么说出口**

> 「都能描述对象类型。主要区别三个：**interface 能声明合并、能被 extends 继承；type 能表达联合类型和交叉类型、能做映射类型**。日常描述对象用 interface，要组合类型用 type。
>
> **我项目里两种都用了，而且用对了地方。** 配置单那种固定形状的对象我用 interface；但 SSE 事件我用的是 type 的联合类型——五个事件分支，每个字段不一样，interface 根本表达不了「五种之一」。
>
> 而且我用的是**可辨识联合**：每个分支都有 `type` 这个字面量字段，所以 switch 判断 type 之后，TypeScript 会自动收窄类型，我写 `evt.text` 它能确认这是 delta 事件。」

**追问｜「声明合并有什么用？」**
> 主要是给第三方库扩展类型。比如你想给 `Window` 加一个属性，就 `declare global { interface Window { electronAPI?: ElectronAPI } }`——**这个必须用 interface，type 做不到。** 我项目里正好有这么一段，为了让渲染进程能类型安全地访问 preload 注入的 API。

## 6｜用过哪些 hooks，useEffect 依赖数组怎么填

**概念**

常用：`useState`、`useEffect`、`useRef`、`useMemo`、`useCallback`、`useContext`。

**useEffect 的第二个参数**：

| 写法 | 时机 |
|---|---|
| 不传 | 每次渲染后都跑 |
| `[]` | 只在挂载时跑一次（卸载时跑 cleanup） |
| `[a, b]` | a 或 b 变化时跑 |

**依赖漏了会怎样**：闭包里读到的是**旧值**（stale closure），这是最常见的 bug。
**依赖多了会怎样**：多跑、可能死循环。

**挂到你的项目**

`App.tsx` 里两个 useEffect：

```ts
// ① 主题应用到根元素 —— 依赖 [theme]
useEffect(() => {
  document.documentElement.classList.toggle('dark', theme === 'dark')
}, [theme])

// ② 首次启动自动新建一个对话 —— 依赖 [conversations.length, newConversation]
useEffect(() => {
  if (conversations.length === 0) newConversation()
}, [conversations.length, newConversation])
```

**第一个是标准用法**：theme 变了才动 DOM。

**第二个值得讲**：为什么依赖是 `conversations.length` 而不是 `conversations`？
因为如果依赖整个数组，每次消息追加数组引用都变，这个 effect 会不停重跑。**只关心「有没有」，所以只依赖长度。**

**怎么说出口**

> 「useState、useEffect、useRef、useCallback 都用过。useEffect 第二个参数是依赖数组：空数组只跑一次，不传每次都跑，传了变量就只在它变化时跑。
>
> **漏依赖会读到旧值，这是最常见的坑**——闭包里拿到的是上次渲染的 state。
>
> 我项目里有个例子：判断「要不要自动新建对话」，我依赖的是 `conversations.length` 而不是 `conversations` 本身。因为**数组每次追加引用都会变，依赖整个数组会导致这个 effect 每来一条消息就跑一次**。我只关心空不空，所以只依赖长度。」

**追问｜「useMemo 和 useCallback 区别？」**
> `useMemo` 缓存**计算结果**，`useCallback` 缓存**函数本身**。`useCallback(fn, deps)` 等价于 `useMemo(() => fn, deps)`。用途都是避免不必要的重算或重渲染。

## 7｜为什么 key 不能用 index ★ 有反转

**概念**

React 靠 key 判断「这一项还是不是原来那一项」。

用 index 当 key 的问题：**位置和身份绑定了**。一旦列表顺序变了（插入、删除、排序），同一个 index 对应的已经不是同一个数据，但 React 认为没变，于是复用错误的 DOM 节点和组件状态。

**具体后果**：输入框内容错位、组件内部 state 串到别的项上、动画重放、全部重新挂载导致性能差。

**挂到你的项目**

`MessageList.tsx` 用的是消息 id：

```tsx
messages.map((m) => <MessageBubble key={m.id} msg={m} />)
```

**这是对的**，因为消息列表会：① 新消息追加 ② 重发时删掉最后一条 ③ 切换会话时整批替换。

**但你项目里也有用 index 的地方**，`ConfigCard.tsx`：

```tsx
{warnings.map((p, i) => <div key={i}>• {p}</div>)}
{problems.map((p, i) => <div key={i}>⚠️ {p}</div>)}
```

**这不是 bug。** 因为这两个列表是：纯展示文本、不增删、不重排、没有内部 state。

**这题的反转就在这里**——被问「你项目里有没有用 index 当 key 的」，诚实说「有，在配置单的静态列表里」，然后讲清楚**为什么那里可以**：

> key 的规则不是「绝对禁止 index」，是「**列表会重排或组件有内部状态时，必须用稳定 id**」。静态展示列表用 index 没有副作用。

**怎么说出口**

> 「用 index 当 key 的话，位置和身份就绑定了。一旦列表顺序变化——插入、删除、排序——同一个 index 对应的已经不是同一条数据，但 React 认为它没变，会复用错误的 DOM 节点和组件状态。**结果就是输入框内容错位、动画重放、性能也差。**
>
> **我消息列表用的是消息 id。** 因为消息会追加、会删掉最后一条重发、切换会话会整批替换，全都会导致位置变化。
>
> 不过我也说实话说，**我项目里确实有用 index 的地方**——配置单里的兼容性问题列表。那个列表是纯文本展示、不增删不重排、没有内部状态，用 index 没问题。
>
> 所以我的理解是：**key 的规则不是绝对禁止 index，是「列表会重排或有内部状态时必须用稳定 id」。**」

**追问｜「那什么情况下 index 一定出问题？」**
> 列表项里有**受控组件**（输入框）或者**内部 state** 的时候。因为 React 复用组件实例，index 不变它就认为还是同一个组件，state 会串到别的数据上。**表单列表用 index 是经典事故。**

## 8｜setState 是同步还是异步

**概念**

React 的 setState 是**批量的**，不是立刻改。

- 事件处理函数里连续多次 setState，会被合并成一次渲染
- React 18 起，Promise、setTimeout 里的更新也自动批处理（之前只有事件处理里批处理）

想拿最新值有两个办法：
1. 函数式更新 `setX(prev => prev + 1)`
2. `useEffect` 里读（渲染完成后）

**挂到你的项目**

流式更新这里你是这样写的：

```ts
onDelta: (d) => set((s) => ({ conversations: patchMessage(s, activeId, assistantMsg.id, {
  content: (当前 content) + d
}) }))
```

**这里必须用函数式**，因为它依赖上一次的 content 来累加。如果用 `set(content + d)` 这种值形式，在批量更新下会拿到旧的 content，**只会保留最后一个 delta，前面的全丢**。

这是流式渲染最容易踩的坑。

**怎么说出口**

> 「setState 是批量的，同一个事件里连续调会合并成一次渲染。要拿最新值就用函数式更新 `setX(prev => ...)`。
>
> **我流式累加文本必须用函数式。** 因为我是在上一次的 content 上追加一个 delta，如果用值形式 `set(content + d)`，在批量更新下拿到的 content 是旧的，**结果就是只保留最后一个分片，前面的全丢**。这是流式最容易踩的坑。」

## 9｜list 和 tuple 的区别

**概念**

| | list | tuple |
|---|---|---|
| 可变 | ✅ 能增删改 | ❌ 不可变 |
| 语法 | `[1,2]` | `(1,2)` |
| 可哈希 | ❌ | ✅ **能当 dict key、能放进 set** |
| 性能 | 稍慢 | 稍快，内存更小 |

**关键**：不可变才可哈希。所以 tuple 能做字典的 key，list 不行。

**挂到你的项目**

**① 你项目里的常量表都是 list 或 tuple**

```python
_RULES: Dict[str, list] = {
    "recommend": ["推荐", "装机", "配置", ...],
    "compare": ["对比", "哪个好", ...],
}
```

关键词表用 list，因为我们只需要遍历，不需要当 key。

**② 你的审计表里单价的 key 是字符串，值是个 dict**

```python
price = DEFAULT_PRICES.get(model) or DEFAULT_PRICES.get(provider) or {"in": 0, "out": 0}
```

如果哪天要做「(provider, model) 组合」的缓存，key 就必须是 tuple——**list 不可哈希，直接报错**。

**怎么说出口**

> 「list 可变、tuple 不可变。**关键区别是不可变才可哈希，所以 tuple 能当字典的 key、能放进 set，list 不行。** 性能上 tuple 稍快、内存更小。
>
> 我项目里关键词表用的是 list，因为只遍历不当 key。但如果我要做「provider 加 model」这种组合缓存，key 就必须是 tuple——**用 list 会直接报 unhashable type**。」

**追问｜「tuple 真的完全不可变吗？」**
> 不能改它自己，但如果里面装了 list，那个 list 还是能改。**所以「不可变」只到第一层**，要真不可变得用 frozenset 或者只装不可变对象。

## 10｜生成器是什么 ★ 第三值钱

**概念**

函数体里有 `yield` 就是生成器。调用它不执行函数体，而是返回一个**迭代器**；每次 `next()` 才执行到下一个 `yield` 并停住，把值抛出来。

**三个好处**：
1. **惰性求值**——用到才算，不把整个结果一次性造进内存
2. **省内存**——处理大文件可以一行行读，不用全 load
3. **能表示无限序列**

**`async generator`**：`async def` + `yield`，配合 `async for` 或手动 `__anext__` 用，是异步流式的基础。

**挂到你的项目**

你的 SSE 接口核心就是一个 **async generator**（`server.py`）：

```python
async def event_stream():
    yield _sse({"type": "status", "session_id": session_id, "routing": result.get("routing")})

    answer = result.get("answer") or ""
    for i in range(0, len(answer), 24):
        yield _sse({"type": "delta", "text": answer[i:i + 24]})
        await asyncio.sleep(0.015)

    if config:
        yield _sse({"type": "config", "config": config})

    yield _sse({"type": "done", ...})

return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**这是流式的本质**：`StreamingResponse` 不会等函数跑完才返回，而是每次拿到一个 yield 值就往外推一次。

**如果不用生成器**，我就得把整个回答拼成一个完整字符串（或者拼成一个大 JSON）再 return，那就完全不是流式了——用户要等全部生成完才看到第一个字。

**怎么说出口**

> 「有 yield 就是生成器，调用不执行、返回迭代器，每次 next 走到下一个 yield 停住。好处是惰性求值，不把整个结果一次性造进内存。
>
> **我的 SSE 接口就是 async generator。** 里面一条条 yield 事件：先 yield 状态，再循环 yield 文本分片，最后 yield 结束事件。
>
> **这是流式的本质**——`StreamingResponse` 拿到一个 yield 值就往外推一次，不是等函数跑完。如果不用生成器，我就得把整个回答拼成完整字符串再返回，用户要等全部生成完才看到第一个字，那就不是流式了。」

**追问｜「生成器和迭代器区别？」**
> 迭代器是实现 `__iter__` 和 `__next__` 的对象；生成器是**写迭代器最省事的方式**——一个 yield 就自动帮你实现了这两个方法。所有生成器都是迭代器，反之不一定。

**追问｜「生成器能做数据处理管道吗？」**
> 能，而且很省内存。`(x*2 for x in data)` 再套 `(x for x in ... if ...)`，可以链式处理百万行数据不爆内存，因为每次只过一个元素。

## 11｜深拷贝和浅拷贝 ★ 有真实坑

**概念**

- **浅拷贝**：只复制第一层，嵌套的对象/数组**还是同一个引用**
- **深拷贝**：递归复制全部，两边完全独立

Python：`copy.copy()` / `copy.deepcopy()`
JS：`{...obj}`、`Object.assign()` 是浅的；`structuredClone()` 是深的

**挂到你的项目**（这题你有最好的素材）

前端解析需求时，`chatStore.ts`：

```ts
function parsePrefsFromText(text: string, base: Prefs): Prefs {
  const out: Prefs = { ...base }        // ← 浅拷贝
  ...
  if (/(不要显示器|不含显示器|无显示器|不要屏幕)/.test(t)) {
    if (!out.exclude.includes('monitor'))
      out.exclude = [...out.exclude, 'monitor']   // ← 新建数组，不是 push
  }
```

**这里有个真坑**：`{ ...base }` 是浅拷贝，`out.exclude` 和 `base.exclude` **指向同一个数组**。

如果写 `out.exclude.push('monitor')`，改的就是 `base.exclude`——而 `base` 是这个会话当前的偏好。**结果是：用户问一句「不要显示器」，历史记录里所有轮次的偏好都被改了。**

代码里用 `[...out.exclude, 'monitor']` **新建数组**，正好躲过这个问题。

**怎么说出口**

> 「浅拷贝只复制第一层，嵌套的数组对象还是同一个引用；深拷贝递归复制全部。
>
> **我项目里正好踩过这个点。** 我解析需求时用 `{...base}` 复制一份偏好，这是浅拷贝——`exclude` 那个数组和原对象是共享的。如果我直接 `push`，改的其实是历史会话的偏好，**用户这一轮说「不要显示器」，前面所有轮次都会被改掉**。
>
> 所以那行我写的是 `out.exclude = [...out.exclude, 'monitor']`，新建一个数组。看着啰嗦，就是为躲这个坑。
>
> 所以我的经验是：**拷贝对象之后，只要里面有数组或子对象，都要问一句「这个引用是不是共享的」。**」

**追问｜「JS 怎么做深拷贝？」**
> `structuredClone()` 是现代标准，能处理嵌套对象、数组、Date、Map。老办法 `JSON.parse(JSON.stringify())` 能用但会丢 undefined、丢函数、Date 变字符串。**手写递归要注意循环引用。**

# 四、数据库（3 题）

## 12｜索引为什么快，底层是什么

**概念**

常见索引是 **B+ 树**。

| 特性 | 为什么重要 |
|---|---|
| 多叉树，一个节点存多个 key | 树高很低（几百万行通常 3 层），一次查询就几次磁盘 IO |
| **非叶子节点只存 key 不存数据** | 一页能放更多 key，树更矮 |
| **叶子节点用双向链表串起来** | 范围查询和排序很快，顺着链表走就行 |
| 数据都在叶子层 | 查询路径长度稳定，不会有的快有的慢 |

对比全表扫描：O(n) 次行比较 → O(log n) 次 IO。

**挂到你的项目**

你的审计表建了三个索引：

```sql
idx_llm_trace   ON audit_llm(trace_id)
idx_llm_session ON audit_llm(session_id)
idx_act_trace   ON audit_action(trace_id)
```

`session_id` 那个就是给「按会话查这次对话的所有调用」用的——没有它，每次查一个会话都要扫全表。

**你踩过的坑（这是加分点）**：

`ok` 字段只有 0 和 1。想给它建索引来「筛失败调用」，但**选择性太差**——查失败的正好是一半数据，走索引要回表几次，还不如直接全表扫。**这种低区分度字段单独建索引没意义，应该建复合索引 `(ok, created_at)`**：先按状态过滤，再按时间排序，一次走完。

**还有一个更隐蔽的**：如果 `created_at` 存的是 Unix 时间戳，按天统计要写 `date(created_at,'unixepoch')`——**函数一套到索引列上，索引就失效了**，退化成全表扫。正确做法是把「查某一天」改写成时间戳范围查询，或者加一个 `day` 字段专门存日期。

**怎么说出口**

> 「索引底层一般是 B+ 树。它快的原因有两个：一是**非叶子节点只存 key 不存数据**，一页能放更多，树就矮，几百万行也就三层，一次查询几次 IO；二是**叶子节点用链表串起来**，范围查询顺着链表走就行。所以从全表扫的 O(n) 变成 O(log n) 次 IO。
>
> **我审计表上踩过一个坑。** `ok` 字段只有 0 和 1，我想给它建索引筛失败调用，后来发现**选择性太差**——查失败正好是一半数据，走索引还得回表，还不如扫表。正确做法是建复合索引，先按状态再按时间。
>
> 还有个更隐蔽的：我时间字段存的是时间戳，按天统计要套 `date()` 函数——**函数包到索引列上索引就失效了**。要么改成范围查询，要么单独加一个日期字段。」

**追问｜「索引越多越好吗？」**
> 不是。索引是拿写入换读取。每次 insert/update 都要维护所有索引的 B+ 树，写放大；还占磁盘。**所以只给「用来定位行」的字段建索引，统计类字段不建。**

**追问｜「什么情况索引会失效？」**
> 四种常见：① 列上用了函数或运算 ② 隐式类型转换（字符串列传数字） ③ `like '%xx'` 前置通配 ④ `or` 连接了没索引的列。**最容易被忽略的是第一种。**

## 13｜事务的 ACID

**概念**

| | 含义 | 举例 |
|---|---|---|
| **A** 原子性 | 要么全成功要么全回滚 | 转账扣钱和加钱必须一起 |
| **C** 一致性 | 约束不被破坏 | 余额不能变成负数 |
| **I** 隔离性 | 并发事务互不干扰 | 两个同时下单不会超卖 |
| **D** 持久性 | 提交后落盘，崩溃也不丢 | 断电后数据还在 |

**隔离级别**（从低到高）：读未提交 → 读已提交 → 可重复读 → 串行化。
级别越高越安全但越慢。MySQL 默认可重复读，Postgres 默认读已提交。

**挂到你的项目（诚实说）**

**你没用复杂事务。** 你的写入都是单条 insert：

```python
def log_llm(self, ...):
    c.execute("INSERT INTO audit_llm ...")   # 单条
```

单条 insert 本身是原子的，不需要显式事务。

**但如果要改，哪里需要？**
如果一次操作要同时写**审计表 + 证据表**（一次工具调用既记成本又存原文），那这两条应该在一个事务里——否则一条成功一条失败，账就对不上了。

**怎么说出口**

> 「ACID 是原子性、一致性、隔离性、持久性。原子性是要么全成功要么全回滚；一致性是约束不被破坏；隔离性是并发互不干扰；持久性是提交后落盘。
>
> **我项目里没用复杂事务**，因为都是单条 insert，本身是原子的。
>
> 但如果要改，我知道哪里该加：**一次工具调用如果既写审计表又写证据表，这两条应该在一个事务里**——不然一条成功一条失败，成本和证据就对不上了。现在我是尽量让它们互相独立，一个失败不影响另一个，但这是「容忍不一致」，不是「保证一致」，**这是我知道的一个设计缺陷。**」

**注意最后这句**——主动说「这是容忍不一致不是保证一致」，比编一个用过事务的故事安全得多，而且显得你真想过。

## 14｜连接查询（join）和你的分库

**概念**

| 类型 | 结果 |
|---|---|
| `INNER JOIN` | 只返回两边都匹配的行 |
| `LEFT JOIN` | 左表全部 + 右表匹配的，没匹配补 NULL |
| `RIGHT JOIN` | 反过来 |
| `FULL JOIN` | 两边全部（MySQL 不支持，要 union 模拟） |

**典型场景**：「查所有用户及其订单，没下过单也要显示」→ `LEFT JOIN`。

**挂到你的项目（诚实说，而且这个答案有观点）**

**你三个库分开，跨库根本不能 join。**

你用的是「拿 id 去另一个库查」：

```python
# 先查会话
sessions = _longterm.recall_dialogue(session_id)
# 再拿 session_id 去审计库查这轮的所有调用
calls = _audit.by_session(session_id)
# 再拿 trace_id 去证据库查原文
evid = _evidence.by_trace(trace_id)
```

**这是「应用层拼装」而不是「数据库 join」。**

好处：各库独立，索引互不影响，一个库锁了不阻塞另一个。
代价：做不了「一次查询拿全」，要在应用层循环，N+1 问题。

**怎么说出口**

> 「内连接只返回两边都匹配的；左连接返回左表全部，右表没匹配的补 NULL。典型场景是「查所有用户及其订单，没下过单也要显示」。
>
> **不过我项目里基本不用 join**，因为我三个库分开了，跨库不能 join。
>
> 我是用 `session_id` 和 `trace_id` 串起来，先查一个再拿 id 去另一个库查，**在应用层拼装**。
>
> 这是有意的取舍：好处是三个库索引互不影响，一个库锁了不阻塞另一个；代价是做不了「一次查询拿全」，而且有 N+1 的风险——比如列十个会话，就得查十一次。
>
> **如果数据量上来，我会改成批量查**：拿到十个 session_id 一次 `where in` 查回来，在内存里按 id 分组，避免 N+1。」

**最后那句很重要**——他说了「如果数据量上来我改成批量查」，这就是**知道自己方案的边界，也知道下一步**。

# 五、HTTP / 网络（2 题）

## 15｜跨域是什么，怎么解决 ★ 你有优势

**概念**

浏览器的**同源策略**：协议、域名、端口，三者有一个不同就算跨域。跨域的 AJAX 请求会被浏览器拦截（**是浏览器拦的，不是服务端拦的**——这个细节常被搞错）。

**三种解决方案**：

| 方案 | 做法 |
|---|---|
| **CORS** | 服务端返回 `Access-Control-Allow-Origin` 等头，浏览器放行 |
| **代理** | 前端请求自己的服务器，由服务器转发到目标（服务端不受同源限制） |
| **JSONP** | 老办法，只支持 GET，用 script 标签绕过 |

**预检请求**：非简单请求（PUT/DELETE、自定义 header、`Content-Type: application/json`）会先发一个 `OPTIONS` 问服务端「允不允许」。

**挂到你的项目**

**你的方案是「代理转发」**，在 Electron 主进程里（`main/index.ts`）：

```ts
ipcMain.handle('backend:proxy', async (_e, options) => {
  const resp = await net.fetch(`${BACKEND_URL}${options.path}`, {...})
  return { status: resp.status, body: await resp.text() }
})
```

**为什么这个能绕过跨域**：Electron 的**主进程是 Node 环境，不是浏览器环境，没有同源策略**。请求从主进程发出去，不受渲染进程的限制。

**而且你还配了 CORS**（`server.py` 里有 `CORSMiddleware`）——**两条路都留着**，因为渲染进程也可能直接 fetch（你的 `api.ts` 就是直接 fetch 到 8766）。

**怎么说出口**

> 「同源策略是浏览器规定的：协议、域名、端口有一个不同就算跨域，AJAX 会被浏览器拦掉——注意**是浏览器拦的，不是服务端拦的**，服务端其实收到了请求。
>
> 解决三种：后端加 CORS 响应头、用代理转发、老的 JSONP。
>
> **我项目里两条都用了。** 渲染进程直接 fetch 到本地后端，靠后端配 CORS；同时主进程还开了一条转发通道——**因为 Electron 主进程是 Node 环境，没有同源策略**，请求从那里发出去不受限制。
>
> 为什么留两条？因为本地桌面应用开发时端口经常变，主进程转发是更稳的兜底。」

**追问｜「CORS 的预检请求是什么？」**
> 非简单请求（PUT、自定义 header、JSON 的 Content-Type）会先发一个 OPTIONS 问服务端允不允许，通过了才发真请求。**所以后端要处理 OPTIONS，不然预检就挂了。**

## 16｜GET 和 POST 的区别，常见状态码

**概念**

| | GET | POST |
|---|---|---|
| 语义 | **获取**资源，幂等 | **提交**数据，不幂等 |
| 参数位置 | URL query | 请求体 |
| 能缓存 | 可以 | 默认不缓存 |
| 长度限制 | 受 URL 长度限制 | 理论上无限（服务端可限） |

**关键不是「哪个安全」，是「语义」**：GET 用来读，POST 用来写。**幂等**是重点——GET 重复请求结果一样，POST 重复请求可能重复下单。

**常见状态码**

| 码 | 含义 | 容易混的地方 |
|---|---|---|
| 200 | 成功 | |
| 201 | 已创建 | POST 新建资源用它 |
| 301 / 302 | 永久 / 临时重定向 | |
| 400 | 请求参数有问题 | **客户端错** |
| 401 | 未认证（没登录） | |
| **403** | 已认证但没权限 | **和 401 常混** |
| 404 | 资源不存在 | |
| 422 | 参数格式对但语义不合法 | |
| 500 | 服务端错误 | |
| 502 / 504 | 网关错 / 网关超时 | 上游挂了 |

**挂到你的项目**

你的接口用了 422（`server.py`）：

```python
raise HTTPException(status_code=422, detail="该预算/用途下无可行配置（预算过低或条件过严）")
```

**为什么用 422 不用 400**：400 是「你的请求本身不合法」（比如 JSON 格式错），422 是「格式对，但语义上做不到」。**「预算太低配不出来」属于后者。**

**你的 `/chat` 用 POST 而不是 GET**——因为要传整段对话和偏好，URL 装不下；而且它语义上不是「读取」，是「触发一次生成」。

**这也解释了你为什么不能用 EventSource**：EventSource 只支持 GET，带不了请求体。

**怎么说出口**

> 「GET 是获取资源、幂等，参数在 URL；POST 是提交数据、不幂等，参数在请求体。**关键不是「哪个安全」，是语义**——幂等意味着重复请求结果一样，所以 GET 能缓存能重试，POST 不能。
>
> 状态码里容易混的是 401 和 403：**401 是没认证（不知道你是谁），403 是认证了但没权限（知道你是谁但不让干）**。
>
> 我项目里用了个 422：预算太低配不出配置的时候返回 422。**因为 400 是「请求本身不合法」，422 是「格式对但语义上做不到」，预算太低属于后者。**
>
> 另外我的对话接口用 POST 不用 GET，因为要传整段对话带请求体——**这也是我前端不能用 EventSource 的原因**，它只支持 GET。」

**追问｜「那你的流式为什么不用 WebSocket？」**
> SSE 是服务端单向推，够用；WebSocket 是双向的，要维护心跳和重连。**AI 对话是「我发一次、它持续往回推」，单向就够，不需要双向。** 真需要双向（比如用户中途插话打断），才上 WS。

| 题 | 怎么说 |
|---|---|
| **事务** | 「原理知道，但我项目里没用复杂事务，都是单条 insert。要加的话，一次工具调用写审计+证据那两条应该在一个事务里——**现在是容忍不一致，不是保证一致。**」 |
| **join** | 「我三个库分开，跨库不能 join，用 id 串、应用层拼装。**代价是有 N+1 风险，量大了我会改成批量 `where in` 查回来在内存分组。**」 |
| **算法** | 「基础题我能写，但没系统刷过。**如果现在要我手撕，我先把暴力解写出来，再说优化方向。**」 |

**「我没用 X」比「我用过 X」安全一百倍**，前提是你能说出「如果用该怎么做」。

# 附录 C：一句话原则

> **概念题不要只答定义，要答「我在哪用过、踩过什么」。**
>
> **答得出用在哪 = 真会；只答出定义 = 背过。**
>
> 而「我没用，但如果用我会这么做」——**是第三种，也是实习生最该用的那一种。**
